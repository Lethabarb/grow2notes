# F05.03 Archive and deactivate end to end

**Outcome:** with every screen, report and export now built, archiving a participant, goal, common item or group, and
deactivating a user, behave exactly as [design.md §3.7](../../design.md#37-archiving-nothing-is-deleted) says
everywhere at once: new work stops, and every existing record stays as it was.

## Stories
- S05.03.01 Archiving keeps every past record unchanged
- S05.03.02 A deactivated person is signed out everywhere and their notes stay

## Feature checks
This feature owns this row in [coverage.md](../coverage.md) (E05). It is linked, not copied:
- design.md §14 M5 *Scope*: archive and deactivate flows checked end to end.

The archive, restore, deactivate and reactivate actions themselves, and their screens, belong to E00 and E01
(participants.md › *Archive and Restore*, common-items.md › *Archive and restore*, users.md › *Detail and actions*).
These stories check the effects across the whole app and fix any gap they find.

As a manager, I want archiving a participant, goal, common item or group to stop it being used for new notes while
every past note, report and export stays exactly as it was, so that archiving never loses or alters a record.

### Acceptance criteria
Already specified elsewhere (linked, not copied):
- [design.md §3.7](../../design.md#37-archiving-nothing-is-deleted): the table rows for Goal, Common item, Common item
  group and Participant, and the rule that nothing is deleted.
- [participants.md › Acceptance criteria › Archive and Restore](../../ux/screens/participants.md#acceptance-criteria)
  and [common-items.md › Acceptance criteria › Archive and restore](../../ux/screens/common-items.md#acceptance-criteria)
  (owned by E01; used here as the starting point).

Specific to this story (end-to-end tests in the test environment, made-up data):
- [x] Given a participant with submitted notes and a draft started today, when a manager archives them: they leave
      Today and search; a worker's and a manager's attempt to start a note for any date gets
      `422 note.participant_archived`; the author can still submit the existing draft.
- [x] After that archive, the participant's history, the text of the daily report for a past date and the text of a
      record export are the same as before it, apart from the "As at" and export time stamps.
- [x] After restore, the participant is back on Today and a new note can be started.
- [x] Given a goal, a common item and a group each archived after a draft was started, the draft and every earlier
      version keep them; a note started afterwards does not show them; reports and exports of earlier notes still
      show them (A3).
- [x] A restored goal, item or group returns at the end of its list (A2); the Every note group cannot be archived
      (A43).
- [x] Any gap found is fixed in this story, with a test.

### Notes
- Built in T24 (24 October 2026) by `PastRecordsTests` (`Grow2Notes.Tests/Platform/PastRecordsTests.cs`), in CI on the
  SQL Server container, each fact in an organisation of its own with made-up data and a clock that stands still, so that
  the report's "As at" line and the export's "Exported by" line are equal and whole texts are compared. No by-hand step
  is added: archiving's by-hand checks are first-use steps 27 and 28 (the archive screen-reader pass), 41 (goal), 45
  (item), 52 (group) and 104 (Past notes after an archive).
- The UI criteria were built and tested in E00 and E01 and are cited, not re-tested: participants.md *Archive and
  Restore* by the `Archive participant` and `An archived participant's page` groups in `ParticipantPage.test.tsx` and
  `tests/e2e/participants.spec.ts`; common-items.md *Archive and restore* by `CommonItemsPage.test.tsx` (archiving and
  restoring an item and a group) and `tests/e2e/common-items.spec.ts`; the archived refusal's sentence, "Jane Citizen is
  archived, so this note cannot be started. Ask a manager.", by `NotePage.test.tsx`.
- Criterion 1: the first fact, `Archiving_a_participant_changes_none_of_their_records_and_restoring_brings_them_back`,
  has the worker's `GET /api/today` list the participant before the archive and not after. Today's search filters that
  list in the SPA and there is no search endpoint, so leaving the list is leaving search (`TodayPage.test.tsx`). One
  detail: the author's own open draft stays under Your unfinished drafts on Today after the archive (design.md §3.7: it
  can still be submitted), which `TodayPage.test.tsx` covers ("lists the draft of a participant archived since"). The
  fact then sends a first save with the lists' version read before the archive, for a worker and a manager on a past
  day, today and tomorrow: all six answer `422 note.participant_archived`, and none created a note. Last, the manager
  submits the existing draft of yesterday and it answers 201. `NoteVersionEndpointsTests` covers a worker's draft
  submitted after an archive.
- The order of the refusals is A97 (T24, R17): an archived participant is refused first, on any date and for either
  role, before the future-date and worker-date rules. That reverses T08's order, which the owner may overturn. The order
  theory in `NoteDraftEndpointsTests.A_first_save_is_refused_for_the_first_check_that_it_fails` holds it, and
  `An_archived_participant_s_first_save_is_refused_and_creates_nothing` is the plain case.
- Criterion 2: the same fact compares the participant's history, the note's read view and version list, the text of
  the daily report for a past date and the text of a record export with earlier versions, before and after the archive,
  and asserts that the report and the export hold the participant's name, so the comparison is not empty. Under the
  frozen clock the stamps are equal, so the whole texts are compared, which is stricter than "apart from" them. The
  participant's own page (`GET /api/participants/{id}`) changes on archive by design and is not in the comparison.
- Criterion 3: the same fact restores the participant with the ETag the archive left: the worker's Today lists them
  again and a first save for today answers 201.
- Criterion 4: the second fact,
  `Archiving_a_goal_an_item_and_a_group_keeps_them_in_earlier_notes_drafts_reports_and_exports`, archives the item, the
  group and the goal after a draft has them ticked. The earlier note's read view and version, the draft's working copy,
  the daily report and the export are equal before and after and hold the goal's text, the group's name and the item's
  text. A new note's template holds none of the three, and a first save with its lists' version answers 201.
- Criterion 5: the restore to the end of the list and the refusal of Every note (`422 config.every_note_fixed`) are in
  `ArchiveGoalEndpointsTests`, `ArchiveCommonItemEndpointsTests` and `ArchiveCommonItemGroupEndpointsTests` (not
  re-tested).
- Criterion 6: the only gap was the order of the refusals (A97). Reports, exports, the read view and the history do not
  filter on a participant's status, an item's archive or a user's status, so nothing else changed in the app.

As a manager, I want a person I deactivate to be signed out on every device at once while their notes keep their
name, so that someone who has left loses access straight away and no record changes.

### Acceptance criteria
Already specified elsewhere (linked, not copied):
- [design.md §3.7](../../design.md#37-archiving-nothing-is-deleted) User row, and
  [§8.6](../../design.md#86-deactivation-reset-and-recovery) *Deactivate*.
- [users.md › Acceptance criteria › Detail and actions](../../ux/screens/users.md#acceptance-criteria--testable-bullets-a-developer-and-tester-can-check) (owned by
  E00; used here as the starting point).

Specific to this story (end-to-end tests in the test environment, made-up data):
- [x] Given a worker signed in on a phone and a laptop (two browser contexts) with a draft open, when a manager
      deactivates them, the next request on each device gets `401` and shows the signed-out-in-place view.
- [x] Signing in again is refused with the same generic message for both setup paths (passkey, and password with a
      6-digit code).
- [x] Their submitted notes still show their name in the read view, Past notes, the daily report and a record export.
- [x] Their open draft stays until a manager discards it from the read view; after that, a new note for that
      participant and day can be started (A9).
- [x] After reactivation they sign in with their existing method, and `user.deactivated` and `user.reactivated` are
      in the audit log.
- [x] Any gap found is fixed in this story, with a test.

### Notes
- The last-manager rule (A26) is checked by E00's users.md criteria and is not repeated here.
- Built in T24 (24 October 2026) by the third fact of `PastRecordsTests`,
  `A_deactivated_worker_is_signed_out_everywhere_keeps_their_notes_and_name_and_signs_in_again_once_reactivated`, in CI
  on the SQL Server container, in an organisation of its own. The by-hand checks are first-use steps 33 to 35
  (deactivate and reactivate on two real devices, with a screen reader), none new.
- The UI criteria were built and tested in E00 and are cited, not re-tested: users.md AC26, AC28 and AC32 by the
  `Deactivate` and `Reactivate` groups in `UserPage.test.tsx` and `tests/e2e/user-actions.spec.ts` (the Deactivate
  dialog with design.md's words, Reactivate with no dialog, and a 401 closing any dialog before the signed-out view).
- Criterion 1: the fact signs the worker in on two devices with `SignedInDevices`, deactivates them as a manager with
  If-Match, and asserts that the device with the draft open and the other device each get `401` that clears the cookie
  on the next request. The "You've been signed out" view, shown in place on a 401, is
  `src/grow2notes-spa/src/routes/signedOutInPlace.test.tsx` and `tests/e2e/sign-in-again.spec.ts`. The e2e suite stubs
  the API, so no single CI test joins the two halves; step 33 joins them by hand on real devices.
- Criterion 2: the fact takes a wrong password's refusal for the same account before the change, then asserts that the
  right password and the passkey each get a refusal equal to it (status, content type, body, and no session cookie), so
  a deactivated account reads like any failed sign-in. The generic sentence, "Sign-in failed. Check your details and try
  again. …", is `SignIn.test.tsx` and `tests/e2e/sign-in.spec.ts`. These two refusals write `auth.locked_out` and
  `auth.signin_failed` by design, so the fact asserts no "no audit row" for them.
- Criterion 3: as a manager, the note's read view gives the author's display name, the history row for the day carries
  it, and the daily report and the record export each hold it in a paragraph.
- Criterion 4: the manager's view of the open draft names the deactivated author; the manager discards it; then a worker
  starts a new note for that participant and day and it answers 201 (A9).
- Criterion 5: a manager reactivates them with a fresh ETag, they sign in with password and code (200), and the audit
  rows about the user hold exactly one `user.deactivated` and one `user.reactivated`. The passkey path is in
  `UserDeactivationEndpointsTests`, which the fact overlaps on purpose, and step 33's last lines.
- Criterion 6: no gap was found. Deactivation leaves `DisplayName` as it is, and no read path filters on the user's
  status.
