# F05.04 Retention and audit extraction runbooks

**Outcome:** the operator has two written, tested procedures in `ops/`: one to find participants whose retention
period may have ended and to destroy records only when the managers decide, with the HPP 4.3 log; and one to extract
audit entries when a manager asks. A manager has read both
([design.md §14 M5](../../design.md#m5-participant-export-audit-completeness-retention), A28, A29).

## Stories
- S05.04.01 Retention and destruction runbook
- S05.04.02 Audit extraction runbook

## Feature checks
This feature owns these rows in [coverage.md](../coverage.md) (E05). They are linked, not copied:
- design.md §14 M5 *Scope*: written runbooks: retention and destruction (with the HPP 4.3 log and the backup note), and
  audit extraction for the operator (A28).
- design.md §14 M5 *Done when*: both runbooks are written and read by a manager.

Both stories are document enablers: done when merged by pull request and read by a manager
([README §9](../README.md#9-definition-of-done) *Short variants*).

Enabler: `ops/retention-and-destruction.md`, with the yearly retention query. So that the operator can give the
managers the yearly list of participants whose retention period may have ended, and any destruction they decide on is
done safely and logged as HPP 4.3 requires (A29, §10.9).

### Acceptance criteria
Already specified elsewhere (linked, not copied):
- [design.md §13 A29](../../design.md#13-assumed-defaults): the retention rule and the yearly list.
- [design.md §12](../../design.md#12-compliance-mapping): the rows for NDIS Act s 45B, APP 11.2 and HRA HPP 4.2 and
  4.3.
- [design.md §10.7](../../design.md#107-backups-and-tested-restore-a36): destroyed records persist in backups until
  they expire and are treated as beyond use.
- [design.md §10.9](../../design.md#109-routine-operations-developer): the yearly task (first relevant in 2033).

Specific to this story:
- [ ] The runbook states the rule in plain English: keep until the latest of 7 years after the last service, age 25
      if any note was written while the participant was under 18, and 7 years after the last NDIS claim for their
      supports. Claim dates are in the invoicing system, so the managers confirm that period (A29, §12).
- [ ] A read-only retention query lists, for each participant, the date of their last submitted note, their date of
      birth, the date each of the first two periods ends, and whether any note was written before they turned 18.
      It runs as the Entra admin (§9.4) and is tested on made-up data in the test environment.
- [ ] The destruction steps run only after the managers have decided, for named participants (§10.9); they run under
      the separate break-glass login (§5.8), in foreign-key order and in one transaction, and say which tables are
      destroyed and that `AuditEvent` rows stay (they hold IDs only and have no foreign keys, §5.3).
- [ ] The HPP 4.3 log records each participant's name, the period covered and the date of deletion, and the runbook
      says where the log and the yearly list are kept (see open questions).
- [ ] The backup note: destroyed records stay in point-in-time backups for up to 35 days and in long-term backups for
      up to 12 months, are treated as beyond use until then, and any restore-drill copy that holds them is deleted
      after the drill (§10.7).
- [ ] If the provider stops using Grow2Notes, the runbook points to the same periods: export each participant's full
      record, or keep the database, before switching it off (§12 HPP 4.2 row).
- [ ] A manager has read it; their name and the date are in the pull request.

### Notes
- The log and the yearly list hold participant names, so they must not be committed to the repository; where they
  live is an owner question.

Enabler: `ops/audit-extraction.md`, with ready-made read-only queries. So that, with no audit screen in v1, the
operator can answer a manager's request for audit entries quickly and the same way every time (A28), including when
preserving evidence after a suspected breach (§9.10).

### Acceptance criteria
Already specified elsewhere (linked, not copied):
- [design.md §13 A28](../../design.md#13-assumed-defaults): what the audit log holds and that the operator extracts
  it on request.
- [design.md §5.3 AuditEvent](../../design.md#auditevent-append-only): the fields and the three indexes.

Specific to this story:
- [ ] Before any query, the operator records in `ops/` who asked, when, why and which query was run, because it is a
      direct production query (§9.4).
- [ ] Read-only queries cover the three indexed questions: one participant's records (by `ParticipantId`), one
      user's actions (by `ActorUserId`), and a date range for the organisation, each filtered by `OrganisationId`.
- [ ] The extract shows times in Melbourne time and resolves user and participant IDs to names for the manager.
- [ ] The runbook says what the log does not hold: opening a note, a participant's history or a version history is
      never recorded (A28), which matters for a breach assessment (§9.10).
- [ ] Each query is tested on made-up data in the test environment.
- [ ] A manager has read it; their name and the date are in the pull request.

### Notes
- Release 2 adds the MCP filters to this runbook (mcp-server.md §9); not part of this story.
- 9 October 2026, from S00.03.03: an audit event is written at least once. If the connection drops after a commit,
  the retry can store the event again with a new `Id` (S00.03.03's Notes), so the extraction tolerates rare
  duplicates: the runbook says that two rows with the same event type, entity, actor and `Details` at the same or
  almost the same time are one event, and no query or count assumes one row per event.
