# F05.01 Participant record export

**Outcome:** a manager opens Export record from a participant, chooses a date range, PDF or Word, and whether to
include earlier versions, and gets one file of that participant's submitted notes to answer an access or correction
request (APP 12, HPP 6). The file is never shown on screen and the app sends it nowhere
([design.md §4.12](../../design.md#412-participant-record-export-managers),
[§11.6](../../design.md#116-participant-record-export-access-and-correction-requests)).

## Stories
- S05.01.01 Export a participant's record
- S05.01.02 Export form checks and failures
- S05.01.03 Include earlier versions in the export
- S05.01.04 One-year export in under 30 seconds on real devices

## Feature checks
This feature owns these rows in [coverage.md](../coverage.md) (E05). They are linked, not copied:
- design.md §14 M5 *Scope*: the participant record export (date range, earlier-versions option, PDF or Word).
- design.md §14 M5 *Done when*: a one-year export with earlier versions for one participant is generated in under 30
  seconds and matches the app.
- [record-export.md › Acceptance criteria](../../ux/screens/record-export.md#acceptance-criteria): *Arrival and
  defaults*, *Validation*, *Export request and results*, *Accessibility and layout*, *Real devices*.

Spanning the stories: the record export and the daily report build each note block with the same code, so the two
files cannot drift apart ([design.md §11.5](../../design.md#115-pdf-and-word-layout)).

As a manager, I want to export one participant's submitted notes for a date range as a PDF or Word file,
so that I can answer their request to see their records within the legal timeframe.

### Acceptance criteria
Already specified elsewhere (linked, not copied):
- [design.md §4.12](../../design.md#412-participant-record-export-managers): the screen's fields, defaults and primary
  action.
- [design.md §11.6](../../design.md#116-participant-record-export-access-and-correction-requests): *Choices*, *Title
  block*, *Body*, *Page setup and footer*, *Audit*.
- [record-export.md › Acceptance criteria](../../ux/screens/record-export.md#acceptance-criteria):
  - *Arrival and defaults*: every bullet. The "box unticked" part of the first bullet arrives with S05.01.03.
  - *Export request and results*: "A valid press sends exactly one…" (with `includeHistory=false`), "A double click,
    or Enter…", "Export never has the `disabled`…", "With a delayed response…", "On `200`, the saved file's name…",
    "An export mocked to take 25 s…", "The download anchor has `rel="noopener"`…", "The Manage nav item…", "The
    Format radios are 40 px…".
  - *Accessibility and layout*: every bullet, with axe run in the default and exported states (the other states
    come with S05.01.02).

Specific to this story:
- [ ] `GET /api/reports/participants/{participantId}/export` has its row in the endpoint matrix test: anonymous `401`,
      worker `403`, a manager of another organisation `404`, manager `200` (design.md §2, §9.2).
- [ ] The file holds only **submitted** notes for that participant whose note dates fall in the range, oldest first,
      each as its current version. Drafts and discarded notes never appear (§11.6).
- [ ] Each note block is built by the same code as the daily report's block (§11.3, §11.5), so common items show the
      Every note group and the picked groups only, by name, in the configured order (D47).
- [ ] A test extracts the text of the PDF and of the Word file for a range holding an edited note, a flagged and
      reviewed note, a past-day note and a note submitted the next day, and both match the stored notes (the M4
      matching test, applied to this file).
- [ ] The M4 font test also passes on a rendered export: every character, including the title block, is in the
      embedded PDF font.
- [ ] The file name holds dates only, for example `participant-record_2026-01-01_to_2026-09-30.pdf`, and the
      document metadata holds the title and organisation only, as for the daily report (§11.5, A19).
- [ ] Each export writes one `participant.exported` audit row with the participant, `from`, `to`, the format and
      `includeHistory=false`, before the response is sent (§5.3, §5.4).
- [ ] The From default comes from the server: the date of the participant's earliest **submitted** note
      (record-export.md Open question 1 settles which response carries it).
- [ ] Given an archived participant, the export screen and the file are the same as for an active one (§3.7).
- [ ] The file is generated in memory and never written to server disk or storage (A19, §7.1).
- [ ] Managers see Export record on Participant detail (active and archived) and on Past notes, opening
      `/manage/participants/{id}/export`; workers never see it ([participants.md](../../ux/screens/participants.md) ›
      Acceptance criteria › Archive and Restore; [participant-notes.md](../../ux/screens/participant-notes.md) ›
      Acceptance criteria › History list, item 11).

### Notes
- This story builds the route, `/manage/participants/{id}/export`, and the Export record links that open it on

- Not Ready until record-export.md Open question 1 (where the earliest submitted note date comes from) is answered.
- Copy marked **(P)** in record-export.md ships with the proposed wording unless the owner has approved other words
  ([README §8](../README.md#8-definition-of-ready)).
- The server-side export rate limit (10 a minute per user, shared with the daily report) is built in S06.01.05; this
  story's `429` handling on screen comes with S05.01.02.
- Owner answer, 9 October 2026: every (P) string in the UX specs on that date is approved as written (D67), so the (P)
  copy above ships as written; it can still be changed later in the copy module. This answers record-export.md Open
  question 5; Open question 1 above is unchanged.

As a manager, I want the export form to tell me exactly what to fix, and what happened when an export cannot be
made, so that I never hand over the wrong range or wait for a file that is not coming.

### Acceptance criteria
Already specified elsewhere (linked, not copied):
- [design.md §4.12](../../design.md#412-participant-record-export-managers) *States*: no notes in the range; To date
  before From date.
- [record-export.md › Acceptance criteria](../../ux/screens/record-export.md#acceptance-criteria):
  - *Validation*: every bullet.
  - *Export request and results*: "On `404` with `code: "report.no_notes"`…", "On a network failure, `5xx` and
    `429`…", "On `403`, no alert…", "On `422` with `errors.to`…", "On `401`, no export message…", "Unmounting during
    a request…", "Changing a date after a result…", "Two identical failures in a row…".
  - *Accessibility and layout*: axe with no violations in the validation-error and failed states.

Specific to this story:
- [ ] Given a missing or incomplete date, a To date before the From date, or a missing or unknown format, the server
      returns `422 validation.failed` with `errors` keyed `from`, `to` or `format`, and writes no file and no audit
      row.
- [ ] Given a range with no submitted notes, the server returns the no-notes response settled by record-export.md
      Open question 2 (assumed `404 report.no_notes`) and no file.
- [ ] A To date after today is handled as settled by record-export.md Open question 3, with a test.

### Notes
- Not Ready until record-export.md Open questions 2 and 3 are answered.

As a manager, I want to include the earlier versions of edited notes in the export, so that a participant asking for
everything we hold, or about a correction, gets the full history.

### Acceptance criteria
Already specified elsewhere (linked, not copied):
- [design.md §11.6](../../design.md#116-participant-record-export-access-and-correction-requests): *With earlier
  versions*, and the title block's "Earlier versions: included" or "not included".
- [record-export.md](../../ux/screens/record-export.md) component 8 (Include earlier versions of edited notes).
- [record-export.md › Acceptance criteria](../../ux/screens/record-export.md#acceptance-criteria) › *Arrival and
  defaults*: the box is unticked on arrival and after returning (first and last bullets).

Specific to this story:
- [ ] With the box ticked, each edited note is followed by "Earlier versions", newest to oldest, each version printed
      in full with its own goals, groups picked, ticks, text and flag, and headed as in §11.6 ("Version 2: saved by
      …", "Version 1: submitted by …").
- [ ] A note with only one version has no "Earlier versions" block.
- [ ] With the box unticked, no earlier version appears anywhere in the file (A20).
- [ ] The text-match test covers every version of an edited note, including a version whose group picks differ from
      the current version and a note corrected after being written on the wrong participant (§3.9).
- [ ] The `participant.exported` audit row records `includeHistory=true` when the box was ticked.

### Notes
- The hint under the box warns that earlier versions can include another person's information; redaction happens on
  the exported Word copy, outside the app (§11.6).

As a manager, I want a full year's record with earlier versions to export in under 30 seconds on my phone or laptop,
so that a large access request does not fail or leave me unsure whether it worked.

### Acceptance criteria
Already specified elsewhere (linked, not copied):
- [design.md §14 M5 *Done when*](../../design.md#m5-participant-export-audit-completeness-retention): the first
  bullet (one-year export with earlier versions, under 30 seconds, matches the app).
- [record-export.md › Acceptance criteria](../../ux/screens/record-export.md#acceptance-criteria) › *Real devices*:
  every bullet.
- [file-download.md](../../ux/components/file-download.md) *Tests to add*: the real-device bullet for a participant
  export taking more than 10 seconds.

Specific to this story:
- [ ] The test data is made up (A35): one participant with a submitted note for every day of one year, some of them
      edited more than once.
- [ ] Measured in the test environment after one warm-up request, so the free database's resume time is not counted
      (§10.3): the PDF and the Word export, each with earlier versions, finish in under 30 seconds from pressing
      Export to the file being handed to the browser.
- [ ] The matching test from S05.01.01 and S05.01.03 passes on the one-year file.
- [ ] If the export is too slow, the fix keeps generation synchronous and in memory, with no stored files and no
      background worker (§7.1, A19).
- [ ] The result of each real-device check, including each manager's laptop date order, is recorded in this story's
      notes.

### Notes
- If a phone cannot save a slow export from the `blob:` URL, apply file-download.md's plain-link contingency to this
  screen only, as record-export.md says.
