# F05.02 Audit log and append-only records

**Outcome:** every event in the audit catalogue is written and found by a test, and the app's own database identity
cannot change or remove note versions, flag reviews or audit entries, so the history meets the 2026 Act's rule
against altering records even if the code has a bug
([design.md §5.4](../../design.md#54-audit-event-catalogue-a28),
[§5.8](../../design.md#58-saving-a-version-history-is-never-changed), [§12](../../design.md#12-compliance-mapping)
s 59AE row).

## Stories
- S05.02.01 Every audit event type is written and found
- S05.02.02 Append-only permissions tested in the database

## Feature checks
This feature owns these rows in [coverage.md](../coverage.md) (E05). They are linked, not copied:
- design.md §14 M5 *Scope*: audit entries for every event in §5.4.
- design.md §14 M5 *Scope*: append-only enforcement through `grow2notes_runtime` (§5.8).
- design.md §14 M5 *Done when*: a test triggers each audit event type and finds its entry.
- design.md §14 M5 *Done when*: the `grow2notes_runtime` test gets error 229 on the listed tables, while deleting a
  `NoteDraft` still works.

Audit entries are added story by story under the Definition of Done ([README §9](../README.md#9-definition-of-done));
this feature proves the whole catalogue at once and keeps it complete.

Enabler: one test that triggers every event type in the audit catalogue and finds its entry. So that the audit log is
complete before go-live, a breach assessment can rely on it (§9.10), and no later change can drop an event unnoticed.

### Acceptance criteria
Already specified elsewhere (linked, not copied):
- [design.md §14 M5 *Done when*](../../design.md#m5-participant-export-audit-completeness-retention): "A test triggers
  each audit event type and finds its entry."
- [design.md §5.4](../../design.md#54-audit-event-catalogue-a28): the full catalogue, including the operator events
  ([§7.4](../../design.md#74-operator-commands)).
- [design.md §5.3 AuditEvent](../../design.md#auditevent-append-only): the fields, and when rows are written.

Specific to this story:
- [x] One table-driven integration test has a row for every event type in §5.4. Each row triggers the event through
      the real endpoint or operator command and finds exactly one new entry with the expected `EventType`,
      `OrganisationId`, `ActorUserId` (null for operator commands), `EntityType` and `EntityId`.
- [x] A guard test fails the build if the event types in the code and the rows in that test differ, so a new event
      type cannot be added without a row.
- [x] Every participant-related event sets `ParticipantId` (§5.3).
- [x] With a unique canary string in a note's Guided notes text and flag reason, no audit row's `Details` contains
      it (A28: never note text).
- [x] A failed sign-in for a known account writes `auth.signin_failed`; one for an unknown email writes no audit row,
      and telemetry gets only a count, with no email address (§5.4).
- [x] Opening a note, a participant's history or a version history writes no audit row (A28).
- [x] A refused change (for example `409 note.version_conflict` or `412 precondition.failed`) writes no audit row,
      because the row commits in the same transaction as the change (§5.3, §5.9).
- [x] Any event type found missing is added in this story.

### Notes
- Release 2 adds MCP events to the same catalogue (mcp-server.md §9); they join this test then, not now (R10).
- Built in T24 (24 October 2026), in CI on the SQL Server container; no by-hand step.
- Criterion 1: `AuditEventsTests.Its_trigger_writes_exactly_one_entry_with_its_fields_and_values` has a row for each of
  the 41 event types in §5.4, and a second row for the extra triggers §5.4 names (`user.setup_link_sent` by Resend
  invite and by Reset sign-in; `common_item.updated` by Reword and by Move). T24 added the nine rows that were missing:
  `auth.signin_succeeded`, `auth.signin_failed`, `auth.mfa_failed`, `auth.locked_out`, `auth.signed_out`,
  `auth.setup_completed`, `report.downloaded`, `participant.exported` and `admin.bootstrap`. Each row finds exactly one
  new entry and compares its organisation, actor, entity, participant and `Details`. The sign-in events have one row
  each, through the password path; their other triggers (passkey, code step, passkey setup) are proved by the exact
  entries in `PasskeySignInEndpointTests`, `TotpSignInEndpointTests`, `PasswordSignInLimitsTests` and
  `SetupPasskeyEndpointTests`. `admin.bootstrap` runs on the shared database in an organisation of its own.
- Criterion 2:
  `AuditTypesTests.Every_event_type_constant_has_a_row_in_the_shared_audit_events_test_and_every_row_a_constant`
  compares the constants with the rows' event types in both directions, names each that differs, and needs no Docker.
  The other tests there already compare the constants with design.md §5.4.
- Criterion 3: each row compares `ParticipantId`, set for `participant.*`, `goal.*`, `note.*` and `participant.exported`
  and null for the rest, `report.downloaded` included.
- Criterion 4:
  `TelemetryCanaryTests.A_canary_in_request_bodies_and_SQL_error_text_appears_in_no_log_telemetry_or_response`
  sends two strings, one for the Guided notes text and one for the flag reason, in the first save and the submit, and
  reads the flow's participant's audit rows: `note.draft_started` and `note.submitted` are among them and no `Details`
  holds either string. The shared canary is not asserted absent, as `participant.created` and `goal.created` record the
  names and the goal text by design.
- Criterion 5: the unknown email's 401, one log entry and no event are in `PasswordSignInEndpointTests`, and the
  unknown credential's in `PasskeySignInEndpointTests` (R07; not re-tested). The known account's `auth.signin_failed` is
  a row of the shared test.
- Criterion 6: the last-event-ID checks in `NoteEndpointTests`, `NoteHistoryEndpointTests` and
  `NoteVersionHistoryEndpointsTests` (R06; not re-tested).
- Criterion 7: the no-audit assertions of the refused changes in `UserDeactivationEndpointsTests`,
  `NoteDraftEndpointsTests`, `NoteDraftCancelEndpointTests`, `NoteDiscardEndpointTests` and the other endpoint tests
  that assert it (R08; not re-tested).
- Criterion 8: nothing was found missing apart from the nine test rows. Every event type was already written.
- By hand, first-use step 15 reads the audit rows in test, and step 31 reads them after the sign-in commands.

Enabler: a test that connects as a member of `grow2notes_runtime` and proves the database refuses to change or remove
history. So that version history, flag reviews and the audit log stay append-only even if application code has a bug
(§9.4, §12 s 59AE row).

### Acceptance criteria
Already specified elsewhere (linked, not copied):
- [design.md §14 M5 *Done when*](../../design.md#m5-participant-export-audit-completeness-retention): the third bullet
  (error 229 for `UPDATE` and `DELETE` on the five append-only tables and for `DELETE` on `Note`; deleting a
  `NoteDraft` still works).
- [design.md §5.8](../../design.md#58-saving-a-version-history-is-never-changed): the grants and denies table.

Specific to this story:
- [x] The test runs on the SQL Server container with a login that is a member of `grow2notes_runtime` only, not the
      schema owner, the same way the app identity is set up in Azure (§10.6).
- [x] `DELETE` on `Participant`, `Goal`, `CommonItemGroup`, `CommonItem`, `Organisation` and `AspNetUsers` also gets
      error 229 (§5.8 *DENY DELETE* row).
- [x] `INSERT` on every append-only table works, and deleting from `AspNetUserTokens` and `AspNetUserPasskeys` works
      (§5.1 *Deletes*), so the app's own writes are not blocked.
- [x] The test's table list is the one place a new append-only table is added (the Definition of Done's "added to the
      M5 permission test"), and a check fails if any `IAppendOnly` entity's table is missing from it.
- [x] In the test environment, the app identity is a member of `grow2notes_runtime` and of no other role, checked once
      as the Entra admin; the result is recorded in this story's notes.

### Notes
- The app-level `IAppendOnly` interceptor (§5.8 *In the app*) was built in S00.03.03; E02 adds `Note`'s column checks
  to it. This story covers the database half, and `RuntimeRoleTests` (S00.03.03) is the starting point for its
  permission test.
- Built in T24 (24 October 2026), in `RuntimeRoleTests`, in CI on the SQL Server container; no by-hand step.
- Criterion 1: the tests run as a database user WITHOUT LOGIN under `EXECUTE AS`, a member of `grow2notes_runtime` only
  and not the schema owner. That is the reading of "a login" (R14): in Azure the app identity is a contained Entra
  database user with no server login either, and permissions are checked on the database user in both places.
- Criterion 2 and the five append-only tables: `AppendOnly` (`AuditEvent`, `NoteReview`, `NoteVersion`,
  `NoteVersionGroup`, `NoteVersionItem`) and `NeverDeleted` (`AspNetUsers`, `CommonItem`, `CommonItemGroup`, `Goal`,
  `Note`, `Organisation`, `Participant`) are the one place a table is named.
  `A_member_of_the_role_gets_error_229_for_a_delete` runs over both lists (12 tables),
  `A_member_of_the_role_gets_error_229_for_an_update` over `AppendOnly` (5), and
  `The_role_has_no_permissions_of_its_own_except_its_denies` compares the role's permissions with the 17 denies
  derived from the two lists.
- Criterion 3: `A_member_of_the_role_can_read_add_and_change_rows_and_delete_an_authenticator_key_a_passkey_and_a_draft`
  adds a `NoteReview` after the `NoteVersion`, adds then deletes an `AspNetUserPasskeys` row, and still deletes a
  `NoteDraft` and an `AspNetUserTokens` row; `A_member_of_the_role_can_add_and_read_an_audit_event` does `AuditEvent`.
- Criterion 4: `Every_IAppendOnly_entity_s_table_is_in_the_append_only_list` reads the app's model, with no connection,
  and fails while an `IAppendOnly` entity's table is not in `AppendOnly`. A new table then needs its denies in a
  migration before the exact-permission test passes, and the 229 theories prove them.
- Criterion 5: done on 9 October 2026 under S00.02.02 (F00.02's notes): the app identity is a direct member of
  `grow2notes_runtime` only, checked as the Entra admin. It is not repeated (R15).
