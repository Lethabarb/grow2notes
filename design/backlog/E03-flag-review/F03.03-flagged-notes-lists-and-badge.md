# F03.03 Flagged notes lists and badge

**Outcome:** managers have one Flagged screen with a **To review** list (oldest first, returned whole) and a
**Reviewed** list (newest first, 30 at a time), and a count badge on the Flagged menu item on every manager screen.
The badge refreshes when a screen loads and when the window regains focus; nothing is pushed, emailed or texted
(D18, A14, [design.md §4.6](../../design.md#46-flagged-notes-managers),
[§6.8](../../design.md#68-session-and-badge-refresh)).

## Stories
- S03.03.01 See the flagged notes to review
- S03.03.02 Switch to the reviewed notes
- S03.03.03 See the To review count on the Flagged menu
- S03.03.04 Show older reviewed notes
- S03.03.05 Keep my place in the Flagged lists

## Feature checks
Rows owned, in [coverage.md](../coverage.md) under E03:
- design.md §14 M3 Scope: "the To review list (oldest first) and badge" and "the Reviewed tab".
- design.md §14 M3 Done when: "A flagged note shows in the list and badge for every manager on their next page load";
  "A reviewed note leaves the list and shows 'Reviewed by … on …' on the note and in the report" (the report part is
  checked by S04.01.04); "Workers get `403` on the review endpoints"; "The codebase has no email, SMS or push
  dependency apart from setup-link email".
- [flagged.md › Acceptance criteria](../../ux/screens/flagged.md#acceptance-criteria): Access and navigation, View
  switch and count, To review list, Reviewed list, Loading and errors, Back and place, The note.
- [app-shell.md › Acceptance criteria › Badge](../../ux/screens/app-shell.md#acceptance-criteria).

flagged.md › Visual and device is marked DoD and is checked on every story here.

Spanning the stories:
- [ ] The endpoint matrix test has rows for `GET /api/reviews?status=toReview`, `GET /api/reviews?status=reviewed`
      and `POST {base}/reviews`: anonymous `401`, worker `403`, manager `2xx`, manager of a second organisation sees
      none of the first organisation's notes.
- [ ] End to end in test: a worker submits a flagged note; a manager sees it in To review and the badge goes up;
      the manager marks it reviewed; the row leaves To review, appears in Reviewed, the badge goes down, and the note
      shows "Reviewed by … on …".

As a manager, I want one list of the submitted notes flagged for a manager and not yet reviewed, oldest first,
so that every flag is seen and dealt with.

### Acceptance criteria
Already specified elsewhere (linked, not copied):
- [design.md §4.6](../../design.md#46-flagged-notes-managers) items 2 and 3 and the empty state;
  [§6.4](../../design.md#64-flag-review-managers), the `GET /api/reviews?status=toReview` row.
- [flagged.md › Acceptance criteria](../../ux/screens/flagged.md#acceptance-criteria):

  - The note (all): the back link reads "Flagged" and pops back to the list.
- [participant-notes.md › Acceptance criteria › Read view](../../ux/screens/participant-notes.md#acceptance-criteria),
  bullet 28a, its Flagged route (S02.04.01 checks the Today and Past notes routes).
- flagged.md *Components* 1 (Flagged as the current nav item), 2, 4 and 7.

Specific to this story:
- [ ] Given a worker, when they call `GET /api/reviews?status=toReview`, then the response is `403`.
- [ ] Only Submitted notes with `FlagStatus = ToReview` are listed; a draft with the flag ticked never appears.
- [ ] `flagReason` and `flaggedAtUtc` come from the version in `FlaggedVersionNumber`, also after a later version
      changed or removed the reason; `flagRemovedLater` is true exactly when the current version is not flagged.
- [ ] Rows are oldest first by `flaggedAtUtc` (see Notes).

### Notes
- "Oldest first" (§4.6, §6.4) names no sort key; this story reads it as the time the note entered To review, which is
  the time each row shows. Confirm at refinement.
- The list is returned whole (§6.1). The shared loading and error region (S00.01.04) is wired here; its states are
  checked for both lists in S03.03.05.
- The note itself is participant-notes.md's read view (E02, with F03.02's review panel); this route changes only the
  back label.

### Acceptance criteria
Already specified elsewhere (linked, not copied):
- [design.md §4.6](../../design.md#46-flagged-notes-managers) *Badge*; [§6.2](../../design.md#62-sign-in-setup-and-session)
  `GET /api/auth/me` (`toReviewCount`); [§6.8](../../design.md#68-session-and-badge-refresh); A14.
- [app-shell.md › Acceptance criteria › Badge](../../ux/screens/app-shell.md#acceptance-criteria) (all).
- [flagged.md › Acceptance criteria](../../ux/screens/flagged.md#acceptance-criteria): the badge halves of the last
  bullets of To review list and of View switch and count.
- [notification-badge.md](../../ux/components/notification-badge.md): the pill and its accessible name.
- [design.md §14 M3](../../design.md#m3-flag-review) Done when bullets 1 ("A flagged note shows in the list and badge
  for every manager…") and 5 ("The codebase has no email, SMS or push dependency…").

Specific to this story:
- [ ] `toReviewCount` is the number of the organisation's notes with `FlagStatus = ToReview`, read through the
      filtered index; it is in a manager's `/me` response and absent from a worker's.
- [ ] Given two managers signed in on different devices, when a worker submits a flagged note, then each manager's
      badge shows the new number on their next screen change or window focus, and no request is sent while they do
      nothing (no polling).
- [ ] An automated check fails the build if the solution references an SMS or push notification package, or if
      anything other than the setup-link sender sends email (§1 Out of scope, A23).

### Notes
- The `/me` refresh triggers come from the app shell (app-shell.md › Refresh, S00.05.03); this story adds
  `toReviewCount` (managers only, as F00.04 expects) and the pill. "When a page loads" is read as every screen change (notification-badge.md; ux/README.md Open question 9).
