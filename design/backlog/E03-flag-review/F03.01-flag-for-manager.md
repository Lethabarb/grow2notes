# F03.01 Flag for manager

**Outcome:** a submitted note with **Flag for manager** ticked and a reason goes into To review. It stays there until
a manager reviews it, even if a later edit removes the tick, and it comes back when a later edit adds a flag or
changes the reason (D18, A15, [design.md §3.6](../../design.md#36-flagging-and-review)).

## Stories
- S03.01.01 Send a submitted flag to To review
- S03.01.02 Return a re-flagged note to To review

## Feature checks
Rows owned, in [coverage.md](../coverage.md) under E03:
- design.md §14 M3 Scope: "the required flag reason" and "the re-review rule (A15)".
- design.md §14 M3 Done when: "A flag removed by a later edit stays in To review until reviewed."

Spanning both stories:
- [ ] One table-driven test runs every row of the flag rules table in
      [design.md §5.8](../../design.md#58-saving-a-version-history-is-never-changed) for version 1 and for later
      versions, from each starting `FlagStatus` (None, ToReview, Reviewed), and checks `FlagStatus` and
      `FlaggedVersionNumber` afterwards.

As a worker, I want a note I submit with **Flag for manager** ticked and a reason to go to the managers' To review
queue,
so that a manager reads the note and deals with it.

### Acceptance criteria
Already specified elsewhere (linked, not copied):
- [design.md §3.6](../../design.md#36-flagging-and-review), first two bullets: the reason is required, up to 200
  characters (A6); managers are alerted only once the note is submitted.
- [design.md §5.8](../../design.md#58-saving-a-version-history-is-never-changed): step 5 (the header update) and the
  first row of the flag rules table (flagged version 1 goes to `ToReview`).
- The reason field, its message and the server's `422` for a missing or over-long reason are built and tested in
  S02.03.02 (E02); this story relies on them.

Specific to this story:
- [ ] A submitted flagged note has `FlagStatus = ToReview` and `FlaggedVersionNumber = 1`, set in the same
      conditional header update as the version (§5.8 step 5), and the `201` response carries `flagStatus`.
- [ ] Given a flagged submit with a blank reason, when `POST {base}/versions` runs, then it is refused with `422`
      (S02.03.02's rule) and the note never reaches To review (M3 Scope: "the required flag reason").
- [ ] A draft with the flag ticked leaves `FlagStatus = None`: a flag on a draft is not seen (§3.6).
- [ ] An unflagged submit leaves `FlagStatus = None` and `FlaggedVersionNumber` null.
- [ ] After a flagged submit, the client invalidates `me` when the response carries a `flagStatus`, so a manager's
      own badge is current when Today shows ([today.md](../../ux/screens/today.md), *Interactions*, the Submit row).

### Notes
- Split with E02: S02.03.02 builds the **Flag for manager** box, the Reason field and the reason rule (M2 Scope:
  "Flag for manager with reason"). This story owns M3's row "the required flag reason" by checking that rule
  end to end, and makes a submitted flag take effect.
- E02 creates the `Note` table whole, with `FlagStatus`, `FlaggedVersionNumber` and the filtered index
  `(OrganisationId, FlagStatus) WHERE FlagStatus = 1` ([design.md §5.3](../../design.md#53-entities)); this story
  starts setting them.
- The badge is S03.03.03. Until then a manager finds a flagged note through the Flagged tag on Today and Past notes
  (E02).

As a manager, I want a note to come back to To review when a later edit adds a flag or changes its reason, and to
stay there when an edit removes the tick, so that no flag leaves the queue without a manager's review.

### Acceptance criteria
Already specified elsewhere (linked, not copied):
- [design.md §3.6](../../design.md#36-flagging-and-review), fourth bullet (A15).
- [design.md §5.8](../../design.md#58-saving-a-version-history-is-never-changed), flag rules table, all four rows,
  applied to Save changes (versions 2 and later).
- [design.md §14 M3](../../design.md#m3-flag-review) Done when: "A flag removed by a later edit stays in To review
  until reviewed."

Specific to this story:
- [ ] Given a note in To review, when an edit saves a version with the flag unticked, then `FlagStatus` stays
      ToReview and `FlaggedVersionNumber` is unchanged, so the list keeps the reason and time it showed.
- [ ] Given a note in Reviewed, when an edit saves a version that is flagged with a changed reason, then `FlagStatus`
      becomes ToReview, `FlaggedVersionNumber` is the new version, and the earlier `NoteReview` row is unchanged.
- [ ] Given a note in Reviewed, when an edit keeps the flag with the same reason, then `FlagStatus` stays Reviewed.
- [ ] Given a submitted note that was never flagged, when an edit adds a flag with a reason, then it enters To review
      with `FlaggedVersionNumber` set to that version.
- [ ] "Reason changed" compares the two versions' stored reasons exactly.
- [ ] The flag change is part of the one conditional header update in §5.8 step 5, so it commits with the version or
      not at all.
- [ ] When a Save changes response changes `flagStatus`, the client invalidates `me`, so the badge is current
      (the badge part of [note-form.md › Acceptance criteria](../../ux/screens/note-form.md#acceptance-criteria)
      bullet 30a; the Flagged lists refetch on mount, S03.03.01).

### Notes
- Leaving To review happens only through a manager's review (S03.02.01); no edit can do it.
