# F03.02 Mark reviewed

**Outcome:** a manager reading a flagged note marks it reviewed with an optional comment; one review is enough
(D24, A14). The review is stored append-only and audited, every note and history list shows whether its flag is To
review or Reviewed, and a review that clashes with another manager or a newer version is refused without losing the
comment ([design.md §3.6](../../design.md#36-flagging-and-review), [§6.4](../../design.md#64-flag-review-managers)).

## Stories
- S03.02.01 Mark a flagged note reviewed
- S03.02.02 See whether a flag has been reviewed
- S03.02.03 Handle a review conflict without losing the comment

## Feature checks
Rows owned, in [coverage.md](../coverage.md) under E03:
- design.md §14 M3 Scope: "Mark reviewed with an optional comment" and "audit of every review".

Spanning the stories:
- [ ] Every path that writes a `NoteReview` row also writes exactly one `note.reviewed` audit entry in the same
      transaction, and no other path writes either (a test runs the success, conflict and retried-press cases).

As a manager, I want to mark a flagged note reviewed, with an optional comment,
so that the flag leaves the To review queue and my review is on record.

### Acceptance criteria
Already specified elsewhere (linked, not copied):
- [design.md §3.6](../../design.md#36-flagging-and-review) third bullet; [§4.6](../../design.md#46-flagged-notes-managers)
  item 3; [§5.8](../../design.md#58-saving-a-version-history-is-never-changed) *Review*;
  [§6.4](../../design.md#64-flag-review-managers) `POST {base}/reviews`; [§5.3](../../design.md#53-entities)
  NoteReview; [§5.4](../../design.md#54-audit-event-catalogue-a28) `note.reviewed`.
- [participant-notes.md › Acceptance criteria › Read view](../../ux/screens/participant-notes.md#acceptance-criteria),
  bullets 21 (its review panel part), 24 ("A manager on a To review note sees the review panel…"), 25 ("A successful
  Mark reviewed replaces the form…"), 28b ("After a successful Mark reviewed, the note refetches…") and 28d ("A busy
  Mark reviewed reads…").
- [review-panel.md](../../ux/components/review-panel.md) *Behaviour* 1–4, 6 and 9, as settled by
  participant-notes.md: no "Earlier reviews" block and no "Go to flagged notes" link.

Specific to this story:
- [ ] Given a manager and a note in To review at version 2, when they send `{versionNumber: 2, comment}`, then the
      response is `201 {reviewedAtUtc}`, `FlagStatus` becomes Reviewed, one `NoteReview` row records version 2, the
      reviewer, the time and the comment (trimmed; blank is stored as null), and one `note.reviewed` audit entry with
      `ParticipantId` set and no note text commits in the same transaction (§5.9).
- [ ] Given a worker, when they call `POST {base}/reviews`, then the response is `403` and nothing is written. Given a
      manager of a second organisation, then `404`.
- [ ] A comment over 500 characters gets `422 validation.failed` with `errors.comment`, and nothing is saved (A6).
- [ ] The migration that adds `NoteReview` denies `UPDATE` and `DELETE` to `grow2notes_runtime`, the table is
      `IAppendOnly`, and it is added to the M5 permission test's list (§5.8;
      [README §9](../README.md#9-definition-of-done), Migrations).
- [ ] After success, the note, `me` and the participant's history queries are invalidated, and so are the review list
      keys once F03.03 adds them (review-panel.md *Behaviour* 4).

### Acceptance criteria

- [design.md §6.3](../../design.md#63-today-participants-and-notes): `flagStatus`, `reviews[]` on `GET {base}` and

  review comment parts).
- [design.md §14 M3](../../design.md#m3-flag-review) Done when bullet 2, the part "shows 'Reviewed by … on …' on the
  note".

Specific to this story:
- [ ] Given a worker, the `GET {base}` and history responses contain no `flagStatus`, `reviews` or review comment
      (an API test, not only hidden on screen).
- [ ] A note reviewed, then flagged again and reviewed again (A15) shows the latest review on the read view, as
      participant-notes.md Open question 1 describes the default build.
- [ ] "Reviewed by … on …" uses the same words and the same date and time format on the note, in the record shown
      after Mark reviewed and in the Reviewed list (one formatter, `microcopy.md`).

As a manager, I want to be told when another manager reviewed the note or someone edited it while I had it open, and
to keep the comment I typed,
so that I never mark reviewed a version I have not read and never lose what I wrote.

### Acceptance criteria
Already specified elsewhere (linked, not copied):
- [design.md §5.8](../../design.md#58-saving-a-version-history-is-never-changed) *Review* and §6.7, the Flag review
  row: `409 review.not_current`.
- [participant-notes.md › Acceptance criteria › Read view](../../ux/screens/participant-notes.md#acceptance-criteria),
  bullets 26 ("Two managers on the same To review note…") and 28c ("Type a comment, press Edit, then Cancel…").
- [review-panel.md](../../ux/components/review-panel.md) *Behaviour* 5 (the three `409` cases and a failed refetch)
  and 8 (the unsent comment, kept in memory only).

Specific to this story:
- [ ] Given manager A opened version 2, when the author saves version 3 before A presses Mark reviewed, then the
      response is `409 review.not_current`, no `NoteReview` row is written, the read view shows version 3, A's
      comment stays in the field and the "edited after you opened it" message shows above the button.
- [ ] Given A's first press reached the server but its response was lost, when A presses again, then the refetch
      shows A's own review and the screen treats it as a success, not a conflict.
- [ ] The unsent comment is never in `localStorage`, `sessionStorage`, IndexedDB, the URL, router state or the page
      title (D22).

### Notes
- Proposed (P) copy for the `409` messages and "Your comment was not saved:" ships as proposed unless the owner
  changes it (participant-notes.md Open question 4).
