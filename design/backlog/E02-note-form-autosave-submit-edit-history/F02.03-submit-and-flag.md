# F02.03 Submit and flag

**Outcome:** the writer submits a note after a check that shows the participant's name and the note date, flagged
for a manager with a short reason when needed. The note is final on submit as version 1, and a draft started on an
earlier day keeps its own date ([design.md §3.4](../../design.md#34-draft-and-submit), §3.6, §3.9, §5.8).

## Stories
- S02.03.01 Submit a note after a name check
- S02.03.02 Flag a note for a manager
- S02.03.03 Submit a draft from an earlier day

As a worker, I want to submit my note after a check that shows the participant's name and the date,
so that the note is final and is not recorded against the wrong person.

### Acceptance criteria
Already specified elsewhere (linked, not copied):
- [design.md §3.4](../../design.md#34-draft-and-submit) (*To submit*, *Final on submit*),
  [§3.9](../../design.md#39-a-note-on-the-wrong-participant) *Prevention*, and §4.3 *Submit confirmation* and "After
  submitting…".
- [design.md §5.8](../../design.md#58-saving-a-version-history-is-never-changed) steps 1–8, and §6.3
  `POST {base}/versions` with `baseVersion = 0` and `Idempotency-Key`.
- [note-form.md › Acceptance criteria](../../ux/screens/note-form.md#acceptance-criteria) › Identity and
  wrong-participant protection: items 4 and 5.
- note-form.md › Validation and Submit: items 20, 21, 22 and 25–30. note-form.md States › Confirmation dialog.
- note-form.md › Autosave: item 11's check that Submit is `aria-disabled` while not saved.
- note-form.md › Edit mode, discard, leaving, session: item 37.
- [today.md › Acceptance criteria](../../ux/screens/today.md#acceptance-criteria) › Focus and navigation: "After
  Submit: the banner is before the `<h1>`…".
- design.md §14 M2 *Done when*: "A worker can fill in and submit a note on a 375 px-wide phone."

Specific to this story:
- [ ] A migration adds `NoteVersion` and `NoteVersionItem` as in §5.3, with unique `(NoteId, VersionNumber)` and
      `(OrganisationId, IdempotencyKey)`. Both are `IAppendOnly`, with `DENY UPDATE, DELETE` for
      `grow2notes_runtime`, and both are added to the table list for E05's permission test (M5).
- [ ] Submit by the author creates version 1: the goal rows are copied from the working copy's snapshot with the
      ticks from the request; the note becomes Submitted with `CurrentVersionNumber = 1` and `FirstSubmittedAtUtc`
      set; the working copy is deleted; `note.submitted` (version number, no text) is written. All in one
      transaction.
- [ ] Only the author can create version 1; anyone else is refused and nothing is created.
- [ ] A retried `POST` with the same `Idempotency-Key` returns `200` with the existing version; no second version.
- [ ] A blank or spaces-only narrative, or one over 20,000 characters, is refused by the server with `422`.
- [ ] The submitted version keeps the goal wording from the draft's snapshot, even after a manager rewords the goal
      (the goal part of the M2 *Done when* reword bullet).
- [ ] Manual check in test at 375 px on a phone: a worker fills in and submits a note.

### Notes

- Before Ready: note-form.md Open question 2 ("Submit the note for" when the note is not today's) and Open question
  10 (Submit after the note was submitted from another tab, built as the "No longer possible" dialog state). The

As a worker, I want to flag a note for a manager with a short reason,
so that a manager knows to look at it.

### Acceptance criteria
Already specified elsewhere (linked, not copied):
- [design.md §3.6](../../design.md#36-flagging-and-review): first bullet (reason required, up to 200 characters), and
  §4.3 item 6.
- [design.md §5.3](../../design.md#53-entities): `IsFlagged` and `FlagReason` in `NoteDraft` and `NoteVersion`;
  §5.8 step 4.
- [note-form.md › Acceptance criteria](../../ux/screens/note-form.md#acceptance-criteria) › Validation and Submit:
  items 23 and 24. note-form.md States › Flag.

Specific to this story:
- [ ] Autosave and Submit send `isFlagged` and `flagReason`. While the box is unticked, `flagReason` is `null`. The
      saved copy of the reason is capped at 200 characters while the screen keeps the full text.
- [ ] The server refuses a flagged version whose reason is blank or over 200 characters with `422`; an unflagged
      version stores no reason.
- [ ] The confirmation shows "Flagged for manager: Yes" or "No", matching what is submitted.
- [ ] A submitted note whose current version is flagged shows the Flagged tag on Today and the flag and its reason on
      the read view (S02.01.03, S02.04.01).

### Notes
- Managers are alerted only after submit, through `Note.FlagStatus`, the To review list and the badge: all E03.
- The field errors are (P) (note-form.md Q5).
- Owner answer, 9 October 2026: every (P) string in the UX specs on that date is approved as written (D67), so the (P)
  copy above ships as written; it can still be changed later in the copy module. This answers note-form.md Q5.

As a worker, I want to finish and submit a draft I started on an earlier day,
so that it is recorded for the day the support happened, with the real submit time shown.

### Acceptance criteria
Already specified elsewhere (linked, not copied):
- [design.md §3.3](../../design.md#33-note-date-and-today) (the note date never changes), §3.4 *Earlier-day drafts*,
  §4.3 state "Draft from an earlier day", and §6.3 (`isPastDayNote` is false for a worker's draft submitted after
  midnight).
- [note-form.md States › Kinds of note](../../ux/screens/note-form.md#kinds-of-note-set-when-the-form-loads): "Draft
  from an earlier day".

Specific to this story:
- [ ] Given a worker's draft dated 30 September and the clock now on 2 October, when they submit it, then version 1
      keeps note date 30 September, `FirstSubmittedAtUtc` is the real time, and `isPastDayNote` is false.
- [ ] The form shows "This draft is for Wednesday 30 September 2026. Submitting it now keeps that date." and the
      indicator "Draft · saved Wed 30 Sep 2026, 9:42 am".
- [ ] The confirmation title reads "Submit the note for", not "Submit today's note for".
- [ ] A draft for a participant archived since can still be submitted (§3.7).

### Notes
- The read view shows the submitted date and time beside the note date (participant-notes.md › Read view, item 19,
  built in S02.04.01).
