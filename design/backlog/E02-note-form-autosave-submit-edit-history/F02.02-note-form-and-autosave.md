# F02.02 Note form and autosave

**Outcome:** a worker or manager opens a participant's note, ticks goals and writes the Guided notes, and every
change is kept on the server, never on the device, through lost connections, sign-outs and a second tab or device.
The server keeps one live note per participant per day and enforces the date rules, and a draft can be discarded to
free the day ([design.md §3.2–3.4](../../design.md#34-draft-and-submit), §5.5, §5.6).

## Stories
- S02.02.01 Melbourne date tests across daylight saving
- S02.02.02 Start a note and autosave the Guided notes
- S02.02.03 Tick the participant's goals
- S02.02.04 Keep autosaving when the connection drops
- S02.02.05 Keep the draft through sign-out and leaving the form
- S02.02.06 Carry on in another tab or on another device
- S02.02.07 One note per participant per day
- S02.02.08 Discard a draft

- [ ] Opening the form writes nothing. The first `PUT {base}/draft` creates the `Note` (Draft) and the author's

- [ ] `GET /api/participants/{participantId}` returns `{id, givenName, familyName, status}`, never the date of birth.
- [ ] Endpoint matrix rows for the three endpoints: anonymous `401`; worker and manager allowed; a manager of a
      second organisation gets `404`.
- [ ] The saved copy of the narrative is capped at 20,000 characters while the screen keeps the full text
      (note-form.md Conflicts resolved 1).

  [§4.3](../../design.md#43-note-form) item 3 with the states "No goals set up" and "Lists changed before the first

- design.md §14 M2 *Done when*: "A goal reworded … after a draft was created does not change that draft or its

Specific to this story:

      goals' IDs, wording and order.
- [ ] The first `PUT` sends `listsVersion`. If it no longer matches, the server returns `409 note.lists_changed` and

      that is not in the stored snapshot returns `422`.
- [ ] Given a draft with the goal "Makes own breakfast", when a manager rewords that goal, then the reopened draft
      still shows "Makes own breakfast" (automated test; the submitted version is checked in S02.03.01).
- [ ] With no goals set up, the form shows "No goals set up for Jane yet. A manager can add them." and the note can
      still be saved.

```yaml
github:

```

As a worker writing on my phone, I want my note to keep saving when the signal drops and comes back,
so that I lose no more than the last few seconds of typing.

### Acceptance criteria
Already specified elsewhere (linked, not copied):
- [design.md §3.4](../../design.md#34-draft-and-submit) *Autosave*: the failed-save banner and retrying.
- [design.md §4.3](../../design.md#43-note-form): the save indicator strings.
- [design.md §5.6](../../design.md#56-working-copies-and-autosave): *Autosave is idempotent under retries* and *Client
  behaviour* (keepalive under 60 KB).
- [note-form.md › Acceptance criteria](../../ux/screens/note-form.md#acceptance-criteria) › Autosave: items 9, 11, 12
  and 13. Item 11's check that Submit is `aria-disabled` is done in S02.03.01.
- design.md §14 M2 *Done when*: "… a save whose response is lost and is retried does not raise a conflict."

Specific to this story:
- [ ] Given a working copy with `LastClientId` X and `LastSeq` 5, when page X sends `seq` 5 again, then the server
      returns `200` with the saved state and changes nothing; `seq` 6 is applied.
- [ ] Given a first `PUT` that committed but whose response was lost, when it is retried, then the server finds the
      caller's own note with the same `clientId` and treats it as an update, not a conflict.
- [ ] Retries follow note-form.md Interactions › Autosave: 1, 2, 4 and 8 seconds, then every 10 seconds; `Retry-After`
      is honoured; 401, 403, 409, 412 and 422 are never retried.
- [ ] When the page is hidden, the latest state is sent at once, with `keepalive` when the body is under 60,000 bytes
      and a normal `fetch` otherwise.

### Notes
- Text typed during an outage lives only in page memory (D22; note-form.md tension 7). No change recommended.
