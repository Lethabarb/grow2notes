# F02.02 Note form and autosave

**Outcome:** a worker or manager opens a participant's note, ticks goals and writes the Guided notes, and every
change is kept on the server, never on the device, through lost connections, sign-outs and a second tab or device.
The server keeps one live note per participant per day and enforces the date rules, and a draft can be discarded to
free the day ([design.md §3.2–3.4](../../design.md#34-draft-and-submit), §5.5, §5.6).

## Stories
- S02.02.01 Melbourne date tests across daylight saving
- S02.02.02 Start a note and autosave the Guided notes
- S02.02.03 Tick the participant's goals
- S02.02.04 Keep autosaving when the connection drops
- S02.02.05 Keep the draft through sign-out and leaving the form
- S02.02.06 Carry on in another tab or on another device
- S02.02.07 One note per participant per day
- S02.02.08 Discard a draft

- design.md §14 M2 *Done when*: "… a save whose response is lost and is retried does not raise a conflict."

Specific to this story:
- [x] Given a working copy with `LastClientId` X and `LastSeq` 5, when page X sends `seq` 5 again, then the server
      returns `200` with the saved state and changes nothing; `seq` 6 is applied.
- [x] Given a first `PUT` that committed but whose response was lost, when it is retried, then the server finds the
      caller's own note with the same `clientId` and treats it as an update, not a conflict.
- [x] Retries follow note-form.md Interactions › Autosave: 1, 2, 4 and 8 seconds, then every 10 seconds; `Retry-After`
      is honoured; 401, 403, 409, 412 and 422 are never retried.
- [x] When the page is hidden, the latest state is sent at once, with `keepalive` when the body is under 60,000 bytes
      and a normal `fetch` otherwise.

### Notes
- Text typed during an outage lives only in page memory (D22; note-form.md tension 7). No change recommended.
- From T10's review (19 October 2026): the retries of the third criterion stop 28 minutes after the person last acted
  on the form, "Not saved" kept, until their next change, blur or return, so that a failing server's answers never
  keep an unattended session alive (A66). The form fetches the antiforgery token as it opens, so that the fourth
  criterion's save as the page is hidden is one request. A first save that never reached the server, retried as the
  page's `seq` 2 on a draft that an earlier page load saved, is sent again as a new page's first rather than raising
  the takeover banner, as §14 M2's lost-and-retried save raises no conflict either (T10's Notes).

### Notes
- Sign-in in place and the 28-minute warning are built in E00 (app-shell.md › Session). This story is the note
  form's side of them.
- Leaving through in-app links uses React Router `useBlocker`, which needs a data router (note-form.md Open question
  12, settled at M0).
- From S00.04.06 (13 October 2026, its task 5): Sign out, in the Account panel (`AccountPanel` in
  `src/routes/Header.tsx`), was built without the autosave flush, as autosave did not exist, and with no stand-in for
  it. This story adds app-shell.md's step 2 of *Press Sign out*: if a note form is mounted, `await autosave.flushNow()`
  before the logout request. If the flush fails, no logout is sent, the panel's status line says "Not signed out: your
  note is not saved yet. Keep this page open; retrying." (app-shell.md *States*, Sign-out blocked: note not saved; (P),
  approved by D67), with its words in `src/copy`, and the button is ready again (*Sign out fails*). The bullet on a
  waiting autosave is linked above: S00.04.06 checked its reload of `/` and Back, but not the `PUT …/draft` before
  the logout, so this story checks the whole bullet again. The comment over `signOut()` that names the missing steps
  then drops this story's part.
- From S00.04.07 (13 October 2026, its task 6): the autosave flush at 28:00, linked above with the first criterion,
  goes through the session clock's hold. S00.04.07 built the clock (`src/api/session.ts`) without it, as autosave did
  not exist, and with no stand-in for it. The clock sets one timer for the next mark, and `holdWhile(promise)` keeps
  the phase as it is until every promise it holds has settled, and then takes the step that the time gives. `api()`
  holds it while each call is out, and gives it the send time of each request answered with anything but a `401`. So
  a save already out at 28:00 holds the warning by itself, and its accepted answer resets the clock. This story adds
  the waiting change's part: at the 28:00 mark, before the phase leaves `active`, the clock has autosave send the
  change now (`flushNow()`) and holds on its promise. An accepted `PUT …/draft` then resets the clock, so no warning
  opens; a failed one leaves the clock to open the 2-minute warning as the hold settles. Its tests use fake timers and
  a fake system time, as `session.test.ts` tests the hold.
- From T10 (19 October 2026, its step 6): the two criteria above are proven in Vitest and in Playwright, signed in for
  real: a change at 27:59 sent at 28:00 with no warning (session-warning.spec.ts); a session ended in place mid-note,
  then the same person signing in again, with one save under the same `clientId` and the next `seq` and no banner, and
  another person landing on Today with nothing sent (note-form.spec.ts); and Sign out with a change waiting, which
  saves it before the logout (sign-out.spec.ts). Handed on: the form's own navigation after Discard's `204` (T12,
  S02.02.08) and after Save changes' or Cancel's success (T14, S02.06.01) calls the leave guard's `leaveFreely()`, as
  Submit's does after its `201`; Discard, Save changes and Cancel are never sent again after a `401`, as T01's Notes
  say; and `['me', 'drafts']` joins `invalidateToday()` as the form unmounts (T12). The manual check above is
  ops/first-use-in-test.md step 61, and step 60 runs the second criterion through the app's own 30 idle minutes: only a
  person can do them, so the manual check stays unticked, and README §9 lets the story be done once CI and the checks
  after the deploy pass.
