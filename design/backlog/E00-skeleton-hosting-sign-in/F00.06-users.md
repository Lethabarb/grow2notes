# F00.06 Users

**Outcome:** managers control who can sign in and in which role: they invite people, resend invites, change a name,
email or role, reset a sign-in, and deactivate or reactivate an account, with the last-manager and one-email rules
held by the server (D23, D24, A26, A27). Users are never deleted.

## Stories
- S00.06.01 See who can sign in
- S00.06.02 Invite a user
- S00.06.03 Resend an invite
- S00.06.04 Reset someone's sign-in
- S00.06.05 Deactivate and reactivate a user
- S00.06.06 Change a user's name, email or role

## Feature checks
Owns these rows in [coverage.md](../coverage.md):
- design.md §14 M0 *Scope*, "Manager screen: invite, edit, reset sign-in, deactivate and reactivate users."
- design.md §14 M0 *Done when*, "After deactivation, the user's next request is rejected (tested)."
- `users.md › Access`, `users.md › List`, `users.md › Invite`, `users.md › Detail and actions`, `users.md › Edit`.

`users.md › General` is a Definition of Done row.

As a manager, I want to resend an invite whose link has expired, so that the person can still set up their account.

### Acceptance criteria
Already specified elsewhere (linked, not copied):
- design.md §4.11 *Resend invite*; §6.6 `POST /api/admin/users/{id}/setup-link` (Invited).
- [users.md](../../ux/screens/users.md) › Acceptance criteria › Detail and actions, AC23 and AC33.

Specific to this story:
- [ ] The new link replaces the old one: the old link now returns `410 auth.setup_link_invalid`.
- [ ] `user.setup_link_sent` is written; a stale `If-Match` returns `412` and sends nothing.

### Notes
- From S00.03.04 (PR #26 review, 9 October 2026): the first user change with `If-Match`; S00.06.04 to S00.06.06 do
  the same. Write the user's `ETag` header with `IfMatch.ETag`, given their `ConcurrencyStamp`; load the user filtered
  by the caller's organisation, so another organisation's is `404` first (users have no query filter, and A48's token
  is only on `ITenantOwned` rows: design.md §5.9 item 5), then call `IfMatch.Check` with the stamp before saving, and
  answer the problem it returns, if any. A save that finds the user changed since loading answers
  `ErrorCode.PreconditionFailed.Problem()`, never `500`: a save through the context throws
  `DbUpdateConcurrencyException`, which the endpoint catches, and `UserManager`'s store catches it itself and returns
  an `IdentityResult` with the `ConcurrencyFailure` error. Add the endpoint's matrix row.
- From S00.03.05 (branch review, 9 October 2026): the invite core, `Invitations.InviteAsync`, only creates a new user,
  then makes its authenticator key, setup token and link. A resend needs a new link for a user who exists, so
  whichever of this story and S00.06.04 is built first splits the key, token and link step out of `InviteAsync`,
  keeping the link's form and its escaped token (S00.03.05's Notes), and both reuse it rather than copy the link.
- From S00.04.02 (13 October 2026, its branch review): the setup enrolment cookie holds the user's security stamp, and
  every setup step after the start compares it (design.md A53), so the resend's stamp rotation also ends a setup that
  the old link started, though its cookie is inside its 30 minutes. Its test can show that: a browser that started
  setup with the old link gets `401` from `POST /api/auth/setup/passkey/options` after the resend.
- Owner answer, 13 October 2026: the client takes the `If-Match` it sends from the user's `concurrencyStamp` in
  `GET /api/admin/users` (D78; design.md §6.6). A person reactivated with no way to sign in is Invited, and this
  story's Resend invite is how they get a link (D75).
- From S01.01.01 (13 October 2026, its whole-branch review), for this story and S00.06.04 to S00.06.06: S01.01.01
  changed `IfMatch.Check`, which the S00.03.04 Note above describes as giving a problem. It is now
  `ErrorCode? IfMatch.Check(StringValues ifMatch, string currentToken)`: the endpoint passes
  `request.Headers.IfMatch` and the user's `ConcurrencyStamp`, and answers the code it gives with `code.Problem()`
  (`PreconditionRequired` is `428`, `PreconditionFailed` `412`); `null` means the change goes on. A handler gives a
  design.md §6.9 code, not an HTTP result, so that Release 2's tools give the same code (mcp-server.md §5.5), and
  takes an `Actor` (`Platform/Actor.cs`; `Actor.InApp` for the app), with the organisation from `ITenantContext`
  (S00.06.01's Note from S01.01.01). S00.06.06's `user.updated` holds the old and new values in `Details` as the
  configuration events do, `{"old": {…}, "new": {…}}` with only the values that changed, named as
  `GET /api/admin/users` names them (`email`, `displayName`, `role`); `ChangeDetails.Of` (`Platform/Configuration/`)
  builds them, and gives none when no value changed (F01.01, S01.01.01's Notes, *Old and new values*).
