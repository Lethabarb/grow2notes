# F00.04 Sign-in, account setup and sessions

**Outcome:** an invited person sets up one sign-in method with MFA from their emailed link, a passkey or a password
plus an authenticator app (D23, A22), and signs in and out on a phone or a laptop. Every request checks the session,
the 30-minute idle and 12-hour limits hold, a warning comes before the idle sign-out, and a person signed out mid-task
signs in again on the same screen.

## Stories
- S00.04.01 Session checked on every request
- S00.04.02 Set up my account with a passkey
- S00.04.03 Set up my account with a password and authenticator app
- S00.04.04 Sign in with a passkey
- S00.04.05 Sign in with email, password and code
- S00.04.06 Sign out
- S00.04.07 Warning before the idle sign-out
- S00.04.08 Sign in again where I was

## Feature checks
Owns these rows in [coverage.md](../coverage.md):
- design.md §14 M0 *Scope*, "Accounts: invite and setup (passkey, or password + TOTP), sign-in and sign-out, cookie
  sessions validated against the security stamp on every request, 30-minute idle timeout with warning, 12-hour
  limit." (Sending the invite is F00.06's; this feature covers accepting it.)
- design.md §14 M0 *Done when*: "A manager and a worker can each accept an invite and sign in with MFA on a phone and a
  laptop, in test, and sign in again a second time (both setup paths)"; "The 12-hour absolute limit and the `org_id`
  claim survive the per-request principal rebuild (tested)"; "Successful and failed sign-ins appear in the audit log";
  "HTTPS only with HSTS; the cookie is HttpOnly, Secure and SameSite=Strict; API responses carry `Cache-Control:
  no-store`."
- `sign-in.md › Sign in`, `sign-in.md › Sign in again, in place`, `sign-in.md › Setup`.
- `app-shell.md › Account and Sign out`, `app-shell.md › Session`.

Feature-level check: the first *Done when* line is a manual check in test, on a real phone and a laptop, for one
manager and one worker on each setup path. The worker's invite comes from the Users screen (S00.06.02).

Enabler: Identity with the design.md §8.4 configuration: the sign-in manager (`CanSignInAsync` requires Status
Active; `auth_time` added once), the claims factory (`org_id`, role and display name rebuilt on every request), the
security stamp checked on every request with `auth_time` carried forward, the 12-hour limit, the `__Host-grow2notes`
cookie, HSTS, and `GET /api/auth/me`. So that deactivation, sign-in resets and role changes take effect on the next
request, and the session limits hold (A24, A34).

### Acceptance criteria
Already specified elsewhere (linked, not copied):
- [design.md §14 M0](../../design.md#m0-skeleton-hosting-sign-in) *Done when*: the 12-hour limit and `org_id` line, and
  the HTTPS, HSTS, cookie and `no-store` line.
- design.md §8.3, §8.4 (configuration and *Claims*), §8.5 (session cookie only, idle and absolute limits).

Specific to this story:
- [ ] Given a session signed in 12 hours and 1 minute ago with steady activity, when it makes a request, then `401`
      (`FakeTimeProvider`).
- [ ] Given a session idle for 30 minutes, then `401`; a request at 29 minutes renews it.
- [ ] Given a manager since made a worker, when their open session calls a manager endpoint, then `403` on that very
      request.
- [ ] `Set-Cookie` shows `__Host-grow2notes` with `Secure`, `HttpOnly`, `SameSite=Strict`, `Path=/`, and no `Expires`
      or `Max-Age`; responses carry `Strict-Transport-Security: max-age=31536000; includeSubDomains`.
- [ ] `/api/auth/me` returns `userId`, `displayName`, `role`, `organisationName` and `today` (from `MelbourneClock`).
      `toReviewCount` is added in E03, and only when the role equals Manager (mcp-server.md §3.5 convention 4).

As an invited worker or manager, I want to set up my account with a passkey from my emailed link,
so that I sign in with my face, fingerprint or phone PIN and never need a password.

### Acceptance criteria
Already specified elsewhere (linked, not copied):
- design.md §4.1 *Setting up an account* steps 1 to 3 and 5, and the expired-link, timed-out and in-app-browser rows.
- design.md §8.1 steps 2 to 5, for the passkey.
- [sign-in.md](../../ux/screens/sign-in.md) › Acceptance criteria › Setup, these bullets: "Opening
  `/setup#u=…&t=…`…", "`410` shows…", "A `401` from any setup call…", "Opening `/setup`, `/setup/password` or
  `/setup/app` with nothing in memory…", "Network failure on the link check…", "View E shows…", "With the CDP virtual
  authenticator…", "With WebAuthn unavailable…", and, for the passkey path, "Both setup paths end on Today…" and
  "After setup, signing in a second time works…".

Specific to this story:
- [ ] `POST /api/auth/setup/start` checks the token once and issues the 30-minute enrolment cookie, valid only on
      `/api/auth/setup/*`; later steps check the cookie and Status Invited, not the token.
- [ ] The passkey creation options require user verification and a discoverable credential, for the environment's
      own domain.
- [ ] Completion is one transaction: the passkey stored, Status Active, `ActivatedAtUtc` and `EmailConfirmed` set,
      the stamp rotated, the person signed in, and `auth.setup_completed` written.
- [ ] Given a completed setup, when the same link is opened again, then `410 auth.setup_link_invalid`; the same for a
      link older than 7 days.
- [ ] The setup endpoints set the tenant from the loaded user, never from the request (design.md §5.9 item 1).

### Notes
- Not Ready until the owner settles sign-in.md open question 7: the fixed passkey `name` sent with `POST
  /api/auth/setup/passkey` (suggested "Grow2Notes"; never shown).
- Until S00.05.01 builds the `/` route, "ends on Today" means setup ends by going to `/`, which S00.01.01's
  client-route fallback serves. S00.05.01 re-checks that both setup paths land on its Today heading, and E02 builds
  Today itself.
- Which phone email apps can create passkeys is the go-live device check in `sign-in.md › Layout and accessibility`
  (a Definition of Done row). S06.02.02 does it once, before go-live.

Specific to this story:
- [ ] `POST /api/auth/login` calls `PasswordSignInAsync` with `lockoutOnFailure: true` and returns `{next: "totp"}`;
      `POST /api/auth/login/totp` calls `TwoFactorAuthenticatorSignInAsync(code, isPersistent: false, rememberClient:
      false)`.
- [ ] Audit: `auth.signin_succeeded`, `auth.signin_failed` (known accounts), `auth.mfa_failed` and `auth.locked_out`;

      generic message shows and `auth.locked_out` was written (A25).
- [ ] There is no "Forgot password", "Remember me" or "remember this device" (A22, design.md §8.2).

### Notes

  them. This story's lockout test is the only one; E06 adds the rate limiter (design.md §9.9, S06.01.05) and does not
  repeat it.
- sign-in.md open question 6: set the two-factor cookie lifetime to 5 minutes explicitly, with a test, or return a
  distinct response for an expired code step. Settle before Ready.
