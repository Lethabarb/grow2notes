# F00.04 Sign-in, account setup and sessions

**Outcome:** an invited person sets up one sign-in method with MFA from their emailed link, a passkey or a password
plus an authenticator app (D23, A22), and signs in and out on a phone or a laptop. Every request checks the session,
the 30-minute idle and 12-hour limits hold, a warning comes before the idle sign-out, and a person signed out mid-task
signs in again on the same screen.

## Stories
- S00.04.01 Session checked on every request
- S00.04.02 Set up my account with a passkey
- S00.04.03 Set up my account with a password and authenticator app
- S00.04.04 Sign in with a passkey
- S00.04.05 Sign in with email, password and code
- S00.04.06 Sign out
- S00.04.07 Warning before the idle sign-out
- S00.04.08 Sign in again where I was

- Chosen here, because design.md is silent:
  - **Claims.** `Grow2NotesClaimsFactory` builds on Identity's `UserClaimsPrincipalFactory`, which gives the user ID,
    the user name, the email and the security stamp, and adds `org_id` under `TenantContext.OrganisationIdClaimType`,
    the role by its `UserRole` name in Identity's role claim type, which the policies compare exactly (S00.03.04), and
    the display name in a claim type of its own, `display_name`. Identity's name claim keeps the user name.
  - **`auth_time`** is the sign-in time from `TimeProvider`, in whole seconds since 1970, as OpenID Connect writes its
    `auth_time` claim. `SessionRules.ValidateAsync` rejects a principal that has none, so a cookie that did not come
    through `Grow2NotesSignInManager`, for example from `HttpContext.SignInAsync` called directly, ends on its next
    request rather than escaping the 12-hour limit (task 6 tests it); so every sign-in goes through the sign-in manager.
    Nothing calls `SignInManager.RefreshSignInAsync`, which also passes through `SignInWithClaimsAsync` and so would
    start a new 12 hours; a story that needs it carries `auth_time` forward first.
  - **The limits, to the second.** The cookie handler treats a session as expired only once its expiry has passed,
    and the 12-hour check rejects more than 12 hours (design.md §8.4, "exceeds"). So a request after exactly 30
    minutes idle, or exactly 12 hours after sign-in, is still let in, and the tests ask for the `401`s at 30 minutes
    and 1 second, and at 12 hours and 1 minute. These times are kept in whole seconds, so the session tests start the
    fake clock on a whole second, as 2026-10-09T13:30Z and `FakeTimeProvider`'s default do.
  - **The stamp check needs the clock to move.** Identity's validator checks the stamp only when more time than
    `ValidationInterval` has passed since the cookie was issued or last renewed, a time the cookie keeps to the second.
    With an interval of zero that is any time at all, so with the real clock every request is checked; but on a
    `FakeTimeProvider` that has not moved since the renewal, a request is not. The tests move the fake clock forward
    at least a second before each request, or a role change could go unseen.
  - **Signing in, in tests, with the real cookie.** No sign-in endpoint exists until S00.04.02, and the seeded users
    have no passkey or password. So a test maps a test-only endpoint, `AllowAnonymous` and outside the `/api` group,
    that loads a user and calls the app's `SignInManager.SignInAsync(user, isPersistent: false)`: the call that ends
    setup (design.md §8.1 step 5), which passes through `SignInWithClaimsAsync`, where every password, code and
    passkey sign-in ends. So the test gets the cookie a real sign-in issues, `auth_time` included, and the session
    tests run the app's own checks on it.
    Calling `HttpContext.SignInAsync` with Identity's scheme was not chosen: it skips the sign-in manager, so the
    session would have no `auth_time` and end on its next request (above), which is all task 6 uses it to show.
    `SignInAsync` does not ask `CanSignInAsync`, so the tests sign in Active users only, as setup does. The cookie is
    `Secure`, so these tests call `https://localhost`, as the antiforgery tests do.
  - **The test-only sign-in beside the cookie**, as the Note above suggests: `Grow2NotesFactory`'s default scheme
    becomes a policy scheme that forwards to `TestSignIn` when a request has `X-Test-User` or `X-Test-Role` (a role
    header alone still fails, as now) and to Identity's cookie otherwise, so a signed-out call meets the cookie's
    `401`, as in the deployed app. `TestSignIn` builds its principal with the app's claims factory and replaces only
    the role claim for `X-Test-Role`. It still skips the session checks, which the cookie tests cover.
    `AppWithoutDatabase` keeps hosting the app as it is deployed, with the cookie alone.
  - **The clock in tests.** A session test hosts the app with a `FakeTimeProvider` in place of `TimeProvider.System`.
    Identity's stamp validator and the cookie handler take `TimeProvider` from the services when their options name
    none, as `SessionRules` and `MelbourneClock` do, so one fake clock drives them all. Data Protection keeps reading
    the real clock, which does not matter here: its keys do not expire within a test run.
  - **HSTS** comes from ASP.NET Core's HSTS middleware (`AddHsts`, `UseHsts`), with a `MaxAge` of 365 days and
    `IncludeSubDomains`, and no `preload`, which design.md §9.7 does not give. §9.7 lists it with the headers that
    S06.01.04's middleware sets on every response, but this story and M0's *Done when* row 6 need it in M0
    (coverage.md), and the built-in middleware is the simplest way. It sends the header only on an HTTPS request, the
    only kind a browser heeds it on (RFC 6797 §7.2, §8.1), so it goes straight after `UseForwardedHeaders`, which
    makes a request that App Service's front end forwarded an HTTPS one. By default it leaves out `localhost`,
    `127.0.0.1` and `[::1]`, so development over `https://localhost` is never pinned, and its test calls another host
    name. A response the exception handler writes goes without it, because the handler clears the response's
    headers first: `DatabaseFailureHandler`'s `500`, an unhandled exception's `500`, and `BadHttpRequestHandler`'s
    `400` and `413`.
    That costs little, as a browser keeps the policy from any earlier response for a year; S06.01.04's header test,
    whose criteria list none of these, decides whether they get it too, and its middleware sets no second header
    (task 8's Note to it).
  - **`role` in `/api/auth/me`** is the `UserRole` name, `Worker` or `Manager`, as the role claim holds it and as most
    UX sketches compare it (`me.role === 'Manager'`). app-shell-nav.md's `Header` sketch compares `'manager'`, which
    a client `Me` type with `role` as a plain string would not catch, so task 5 hands S00.05.01 a Note to compare the
    name as the API gives it. The organisation's name is read through `ITenantContext`, so the endpoint also shows
    that the rebuilt principal's `org_id` is the request's tenant.
  - **Of design.md §8.4's block**, this story adds the sign-in manager, the claims factory, authentication with
    Identity's cookies, the stamp validator options and the session cookie. The password rules, lockout, the token
    providers and the passkey options come with the first story that uses each, such as S00.03.05's setup link and
    S00.04.05's lockout (its Notes).
  - `Grow2NotesSignInManager`, `Grow2NotesClaimsFactory`, `SessionRules` and `/api/auth/me` go in `Features/Auth/`
    (design.md §7.3: "sign-in, setup, passkeys, TOTP, session"), HSTS in `Program.cs`, and the policy scheme and the

- No audit event: design.md §5.4 has none for a session check. A session that ends at a limit or after a stamp change

- The stamp check runs on every request that carries the cookie, as design.md §8.4 asks, static files included:
  `UseAuthentication` authenticates each request, and the browser sends the cookie with the page's own asset
  requests. So each of a page load's few asset requests reads the user once and renews the cookie. That is accepted,
  as the hashed assets are fetched once and then cached. The cookie handler marks a response that renews the cookie
  `no-cache,no-store`, with `Pragma: no-cache` and an `Expires` in 1970. `CacheHeaders` has the last word on
  `Cache-Control`, and on a hashed asset also removes `Pragma` and `Expires`, without which Chromium and WebKit would
  revalidate the bundle on every signed-in load. A page or asset response that sets a cookie, as a renewal does, is
  `private` (`private, max-age=31536000, immutable` for an asset, `private, no-cache` for `index.html`), because a
  `Set-Cookie` does not stop a shared cache from keeping a response (RFC 9111 §7.3); one that sets none keeps design.md
  §7.2's `public` and `no-cache` (PR #28 review, A50).
