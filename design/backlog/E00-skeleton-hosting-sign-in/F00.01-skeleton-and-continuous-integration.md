# F00.01 Skeleton and continuous integration

**Outcome:** one ASP.NET Core 10 app serves the React SPA and the API from the same origin, every pull request is
built and tested in CI, and the shared building blocks that every screen uses (tokens, buttons, loading and error
handling, the copy module and its checks) exist once.

## Stories
- S00.01.01 Serve the SPA and the API from one origin
- S00.01.02 Build and test every pull request
- S00.01.03 Shared look, buttons and page status
- S00.01.04 Shared loading, failure and form-error handling
- S00.01.05 Copy module, date formats and wording checks

## Feature checks
Owns this row in [coverage.md](../coverage.md): design.md §14 M0 *Scope*, "ASP.NET Core on .NET 10 LTS serving the
React (Vite, TypeScript) build from the same origin; unknown `/api` paths return 404."

The building blocks in S00.01.03–S00.01.05 own no coverage row of their own. They are the first build of mechanisms
that the Definition of Done ([README §9](../README.md#9-definition-of-done)) checks on every story.

Specific to this story:
- [ ] The query client has no persister; `refetchOnWindowFocus` is off by default; queries retry once, silently, on
      a network failure, a timeout or a `5xx`; mutations never retry.
- [ ] A load that fails shows "[Thing] did not load: no connection. Try again."; a failed Try again shows "[Thing]
      still did not load: no connection. Try again." (Vitest with fake timers).
- [ ] The error summary is first in `<main>`, above the `<h1>`, takes focus on a failed submit, and its links focus
      their field without changing the URL; the page title gains "Error: ".
- [ ] Every `POST`, `PUT` and `DELETE` sends `X-XSRF-TOKEN` from memory (design.md §9.8).
- [ ] A `401` from any call except `/api/auth/login*`, `/api/auth/setup/*` and `/api/auth/logout` raises the
      session-ended event that S00.04.08 listens for.

### Notes
- From S00.03.04 (PR #26 review, 9 October 2026): CI's end-to-end run serves `http://localhost:5000`, but the
  antiforgery endpoint and every token check need HTTPS, because the antiforgery cookie is `Secure`. Before the
  `api()` wrapper calls them there, the run serves HTTPS, or sends `X-Forwarded-Proto: https`, which the app trusts
  from loopback, and the browser must then still keep the `Secure` cookie. The token comes in the `X-XSRF-TOKEN`
  response header of the endpoint's `204`; a browser's navigation to the endpoint, or a request that its `Sec-Fetch-*`
  headers say comes from another origin, gets `403`, so the wrapper fetches the token from the SPA's own origin. A
  missing or stale token gets `400` problem+json with no `code`, and a body that is not JSON `415`. The wrapper
  fetches a fresh token after sign-in, and when a `POST`, `PUT` or `DELETE` gets a `400` with no `code`, as the `/api`
  filter answers a missing or stale token, it fetches a fresh token and retries once. It sends `If-Match` as exactly
  one quoted value, the `ETag` as the server wrote it (`IfMatch.ETag`).
