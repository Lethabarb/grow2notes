# F00.03 Tenancy, audit and operator commands

**Outcome:** every tenant-owned row belongs to one organisation, and the model, the database and the tests keep it
there (D3); every state change can write its audit entry in the same transaction (A28); requests are denied by
default; and the operator can create the organisation with its first manager, and break glass when needed.

## Stories
- S00.03.01 Database context, conventions and first migration
- S00.03.02 Tenant isolation and its tests
- S00.03.03 Audit writer
- S00.03.04 Deny by default, CSRF and the endpoint matrix
- S00.03.05 Bootstrap the organisation and first manager
- S00.03.06 Break-glass reset and sign-out of everyone

## Feature checks
Owns these rows in [coverage.md](../coverage.md):
- design.md §14 M0 *Scope*, "The Organisation table, `OrganisationId` on every `ITenantOwned` entity with the named
  query filter, and the `grow2notes_runtime` database role (D3)."
- design.md §14 M0 *Scope*, "The audit table, starting with sign-in and user events. The operator commands." (The
  sign-in events are written by F00.04's stories and the user events by F00.06's; this feature builds the table and
  the writer.)
- design.md §14 M0 *Done when*, "A test fails the build if any `ITenantOwned` entity lacks the organisation filter; the
  named exceptions (`AspNetUsers`, Identity child tables, `DataProtectionKeys`) are listed in the test."

### Notes
- Sprint 02, 8 October 2026: refined to Ready and pulled into Sprint 02, as its plan allows (sprint-02.md, Plan).
  Sized again against the reference stories (releases.md) and S00.03.01 (5 points): more parts than Reword a goal, but
  no endpoint, screen or audit event, and less than S00.03.01, so it stays at 3. The linked §5.9 and §9.2 groups were
  narrowed to what this story builds.
- No entity in the model is `ITenantOwned` yet. S00.03.03's `AuditEvent` has `OrganisationId` and is not a named
  exception, so the model test makes it the first; E01's configuration tables follow. Until then the query filter,
  the interceptor and the composite foreign key rule are proven on stand-in entities in a test-only context and
  database, as `ModelConventionsOnNewEntitiesTests` does for the design.md §5.1 conventions, and the model test finds
  only the named exceptions in the app's own model. The test lists `Organisation` with them: it is the tenant, not
  tenant-owned (design.md §5.3).
- The composite foreign key "convention" is the design.md §5.1 *Tenancy* rule. Each relationship is configured
  explicitly, as the §5.10 sketch shows, and the model test enforces the rule; foreign keys to `Organisation` itself
  are single-column. No EF Core convention rewrites foreign keys: design.md names none, and the explicit pattern is
  the simpler one to read.
- Chosen here, because design.md names no folder: the operator commands go in
  `src/Grow2Notes.Web/Platform/OperatorCommands/` (design.md §7.3 puts them in `Platform/`), the only place where the
  source test allows `IgnoreQueryFilters`. S00.03.05 and S00.03.06 create them there.
- What later stories take from this one: S00.04.01's claims factory adds the `org_id` claim under this story's
  constant; the sign-in and setup endpoints (S00.04.02 to S00.04.05) and the operator commands (S00.03.05, S00.03.06)
  set the tenant with `ITenantContext.Use` from the user or organisation they have loaded, which also works outside a
  request; S00.03.03's audit writer passes its `OrganisationId`, which the interceptor checks against the tenant;
  S00.03.04's endpoint matrix calls as the seeded users (how it signs them in is its own); and `AspNetUsers` stays
  unfiltered, so S00.06.01 filters it explicitly.
- No migration: query filters are not part of the migrations' model, and no entity is tenant-owned yet, so the deploy
  applies none and CI's pending-model-changes check stays clean.
- 8 October 2026, task 4: probing the stand-ins found a gap in design.md §5.9 item 3, and a second, separate probe
  confirmed it. Under organisation A's tenant, `Update` of a stand-in parent made up with the ID of B's parent and A's
  `OrganisationId` saved without error and changed B's row: the interceptor goes by the `OrganisationId` a row carries,
  which was A's, and EF Core's `UPDATE` matched the primary key alone, since query filters do not reach updates. Decided
  here (D67), by the developer, for the owner to overturn: `OrganisationId` is a concurrency token on every
  `ITenantOwned` entity type, set with the query filter in `TenantQueryFilter.Apply`, so EF Core's `UPDATE` and `DELETE`
  also match the original `OrganisationId`, which the interceptor already holds to the tenant. A made-up row now matches
  no row, and the save throws `DbUpdateConcurrencyException` with nothing written. design.md §5.9 item 3 and the §5.10
  sketch say so. The stand-in tests prove it for an update and a delete, which both fail without the token, and that the
  tenant's own loaded rows still update and delete. A concurrency token changes no column: a tenant-owned entity's
  migration records it in the model snapshot, with no schema change. It sits beside the `RowVersion` of design.md §6.7,
  since EF Core matches every token of a row, and an endpoint that answers `412` to the exception stays right, because
  it loads its row through the query filter first.

      endpoint behind the fallback policy, then `403`.
- [ ] A `POST`, `PUT` or `DELETE` without a valid `X-XSRF-TOKEN` is refused, and a form-encoded body is refused.
- [ ] The `If-Match` helper returns `428` when the header is missing and `412` when it is stale (unit tests).

- From S00.01.01: an unhandled exception in Production currently gives Kestrel's bare empty `500`; the problem+json

- From S00.02.03 (Sprint 02 planning): `deploy.yml` smoke-tests only `/healthz`, because `/api/auth/antiforgery` does
