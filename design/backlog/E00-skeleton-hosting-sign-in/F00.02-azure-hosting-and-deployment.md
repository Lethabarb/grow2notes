# F00.02 Azure hosting and deployment

**Outcome:** the test and production environments run in Azure Australia Southeast from Bicep, with no stored
secrets; every merge to `main` reaches test, production deploys are run by hand, telemetry carries IDs only, and
setup links can be emailed.

## Stories
- S00.02.01 Bootstrap Azure for both environments
- S00.02.02 Test environment resources
- S00.02.03 Deploy to test from main
- S00.02.04 Production environment and manual deploy
- S00.02.05 Database delete lock
- S00.02.06 Server telemetry with IDs only
- S00.02.07 Setup-link email

## Feature checks
Owns these rows in [coverage.md](../coverage.md):
- design.md §14 M0 *Scope*, "EF Core and Azure SQL in Australia Southeast, Key Vault, the user-assigned identity, Bicep
  (`bootstrap`, `main`, `locks`) and GitHub Actions deploying to test and prod." (The EF Core context itself is built
  in S00.03.01.)
- design.md §14 M0 *Scope*, "Telemetry in Australia Southeast that never records request bodies or SQL error text."
- design.md §14 M0 *Done when*, "Deleting the test SQL server is refused while its database is locked (or the fallback
  in §10.1 is recorded)."

Backups beyond the platform defaults (35-day point-in-time restore, monthly long-term retention, the restore test)
and the uptime and error alerts are E06's (design.md §14 M6 *Scope*, Backups and Monitoring).

Enabler: `infra/bootstrap.bicep`, run once by the developer as subscription Owner: the test and prod resource groups;
a deployment identity per environment with an OIDC federated credential and Contributor on its own group; the app's
user-assigned identity per environment with its role assignments; Azure Policy *Allowed locations*; the budget alert.
So that the pipeline deploys with no stored secrets, and nothing can be created outside Australia (D33, D38).

### Acceptance criteria
Already specified elsewhere (linked, not copied):
- design.md §10.5, the `bootstrap.bicep` line and the paragraph on `Microsoft.Authorization` resources.
- design.md §9.4, "GitHub Actions → Azure" and "Key Vault" bullets.
- design.md §10.1, rows Resource group, User-assigned managed identity and Governance.

Specific to this story:
- [ ] Creating a resource in any region other than Australia Southeast or Australia East is refused by policy (try one
      in the test group).
- [ ] Each federated credential trusts only `repo:<owner>/<repo>:environment:<env>`; GitHub holds only non-secret IDs,
      and no client secret or publish profile exists.
- [ ] A deployment identity cannot create a role assignment or a lock (an attempt fails).
- [ ] The budget alert is set at AUD 100 a month, and Defender for Cloud's free posture checks are on.

### Notes
- The subscription is the operator's (D40). The hosting agreement is a go-live checklist line for E06.

### Acceptance criteria
Already specified elsewhere (linked, not copied):
- design.md §10.1, the production resource table.
- design.md §10.4 `deploy.yml`, the production trigger and the approval paragraph.

Specific to this story:
- [ ] The production deploy refuses a CI run that has no successful deployment to test.
- [ ] The `prod` environment accepts deployments only from `main`.
- [ ] Production has its own identities; no test identity can reach a production resource.
- [ ] `IdentityPasskeyOptions.ServerDomain` in production is the production domain (design.md §8.4).
- [ ] `sql/grant-identities.sql` is run once for production before its first migration, and `locks.bicep` once after
      its first deploy, putting `CanNotDelete` on the production database (design.md §10.5).

### Notes
- Not Ready until the owner has fixed the production domain, a Grow2Notes domain (A38). It must not change after the
  first real passkey is enrolled.
- A private repository needs GitHub Pro or Team for the environment branch restriction (design.md §10.2, §10.4).
- The 35-day point-in-time restore and the monthly long-term retention are set by E06 (M6 *Scope*, Backups;
  S06.03.01). S06.05.01 checks production against design.md §10.1 before any real data goes in.

Enabler: `infra/locks.bicep`, run once by the developer as Owner on the test environment, putting a `CanNotDelete`
lock on the test database; then the check, in test, of whether deleting the SQL server is refused while its database
is locked. So that a mistaken delete cannot remove the test database, and the last M0 *Done when* line is answered.
Production does not exist yet; S00.02.04 runs the same file once after production's first deploy.

### Acceptance criteria
Already specified elsewhere (linked, not copied):
- [design.md §14 M0](../../design.md#m0-skeleton-hosting-sign-in) *Done when*, "Deleting the test SQL server is
  refused while its database is locked (or the fallback in §10.1 is recorded)."
- design.md §10.1, the paragraph after the table.

Specific to this story:
- [ ] The result of trying to delete the test SQL server, and its date, is recorded in this story's Notes; if the
      delete was not refused, design.md §10.1 is updated to say that long-term backups are the protection.
- [ ] With the lock in place, the pipeline still adds and removes its temporary firewall rule.
- [ ] `main.bicep` contains no `Microsoft.Authorization` resources.
