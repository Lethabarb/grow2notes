# F00.07 Sign-in choices

**Outcome:** at setup, anyone invited (a worker, a manager or Support) can choose how they sign in: a passkey, a
password and an authenticator app, a password only, or a password and a passkey (D97). A second step is offered to
everyone and required of no one. The first two work exactly as before; this feature adds the other two.

## Stories
- S00.07.01 Set up and sign in with a password only
- S00.07.02 Set up and sign in with a password and a passkey

## Feature checks
Owns these rows in [coverage.md](../coverage.md), linked and not copied:
- design.md §14 M0 *Done when*, "A manager and a worker can each accept an invite and sign in ... (both setup
  paths)", now every setup path (D97).
- D97: the four ways to sign in, and the amended rules in D23, D51, A22, A34 and design.md §8.1.

As an invited person, I want to choose a password alone as my way to sign in, so that signing in is my email and
password and nothing else.

Requested by the owner on 1 November 2026: "we need to have username and password, nothing extra, as an option". The
ids in brackets are the T42 plan's requirement ids.

### Acceptance criteria
Already specified elsewhere (linked, not copied):
- [sign-in.md](../../ux/screens/sign-in.md) and [design.md §8](../../design.md#8-security-and-authentication) as
  D97 amends them.

Specific to this story:
- [ ] Setup view E lists four plain choices in this order: a passkey (still the recommended one), a password and an
      authenticator app, a password only, and a password and a passkey. The password-only choice is not marked
      recommended. In a browser with no passkey support only the two password choices are offered, with the existing
      notice. (R01, R17)
- [ ] Everyone may choose any of the four: workers, managers and Support. There is no role check and no organisation
      setting that limits the choice. (R02)
- [ ] Choosing a password only takes the person from view E to Create a password and then finishes setup at once, with
      no authenticator step and no code. They are signed in on Today, and Back leaves the app. The password rules are
      the same as for the other methods. (R05)
- [ ] Setup for a password only is refused as the other paths are: an old or ended link, or a person who is not
      Invited, gets 401, and a password that fails the rules gets 422 under the password field. Completion is one
      all-or-nothing step: the person becomes Active, the link stops working and `auth.setup_completed` is written.
      (R07)
- [ ] Signing in is the email and password only, with no second screen, then Today. The five-attempt lockout of 15
      minutes, the per-account and per-address limits, the generic failure message and the failure events are as for
      the other methods. (R08)
- [ ] Every successful sign-in writes `auth.signin_succeeded`, a password-only one included, and if the event cannot be
      written no session starts. A person who chose a second step never skips it: a password alone signs in only a
      person who chose it. (R09, R13)
- [ ] The passkey-only and the password-and-app methods behave exactly as before: same endpoints, bodies, refusals,
      screens and flow, and a setup request for the app method with no code is still refused. (R03, R04)
- [ ] Reset sign-in and reactivation work for this person without change, and no screen shows or changes anyone's
      method. (R24, R25)
- [ ] No new audit event type is added. Nothing about the email, password or method is kept in browser storage,
      cookies set by script, history state or the URL. (R26, R28)
- [ ] The changed screens pass axe, work by keyboard alone and work at 375 px and on a laptop, and Enter in the password
      field never opens a passkey prompt. (R31)
- [ ] Existing tests change only where their rule changed, and the pull request names each (R30). Server, SPA and
      end-to-end tests cover a password-only setup then a second sign-in, with the (a) and (b) tests unchanged. (R29)
      Check: the automated tests the T42 plan lists, and the by-hand steps on ops/first-use-in-test.md.

### Notes
Planned on 1 November 2026. Each criterion's test is named in the T42 section of tasks.md when it is built.

As an invited person, I want to choose a password and then a passkey as my way to sign in, so that my password alone
is not enough and I use my device's prompt as the second step.

Requested by the owner on 1 November 2026 (answer 2 of 3). The ids in brackets are the T42 plan's requirement ids.

### Acceptance criteria
Already specified elsewhere (linked, not copied):
- [passkey-flows.md](../../ux/components/passkey-flows.md) and design.md §8 as D97 amends them.

Specific to this story:
- [ ] Choosing a password and a passkey takes the person to Create a password and then straight to the device's passkey
      prompt, then finishes setup and signs them in on Today. Setup is one all-or-nothing step: the password and the
      passkey are both added, the person becomes Active, the link stops working and `auth.setup_completed` is
      written. A cancelled or failed prompt can be tried again without retyping the password, and no half-finished
      account is made. (R06)
- [ ] The attestation must belong to the person who owns the setup link, and a passkey made for anyone else is
      refused. The other refusals are as for the other paths. (R07)
- [ ] Signing in: after an accepted password the screen asks for the passkey with a button. Pressing it opens the
      device's prompt for that account's passkey, and success signs the person in on Today. A passkey of another
      account never signs the person in. (R10)
- [ ] After a cancelled or failed prompt the person can try again, or type the password again, and the page's own
      "Sign in with a passkey" button stays available. A cancelled prompt shows nothing alarming, and the page never
      starts a prompt on its own. (R11)
- [ ] The authenticator key that every invite creates never lets this person sign in with a 6-digit code: the code
      step is refused for a passkey holder. (R12)
- [ ] The passkey step works only straight after an accepted password and is refused for an account with no passkey.
      It uses the code step's per-account limit, sits in the sign-in request-limit group and lasts the existing 5
      minutes. The new endpoints are in the endpoint matrix and are shown as failed sign-ins when they answer 401, and
      the sign-in screens give the new calls the long timeout PR #211 gives the others. (R14, R27)
- [ ] The page's "Sign in with a passkey" button signs this person in with the passkey alone (A142), so this method is
      no stronger than a passkey alone, and the 5 minutes count from the passkey options request, about a second after
      the accepted password. Both are said plainly in D97 and design.md §8. (R15, R16)
- [ ] D97 is recorded in decisions.md, dated 2026-11-01 after D95, amending D23, D51, A22, A34, design.md §8.1's
      invariant, the privacy table row for APP 11.1 / HPP 4.1 and ops/security-review.md. (R18)
- [ ] The specs agree with D97: design.md (summary, roles, §4.1, §5.3, §6.2, §8, §9.9, §12, §13, §14), the UX specs
      with every new string marked (P) and listed in the pull request for the owner (D67), the backlog and
      coverage.md, ops/security-review.md with a dated amendment, and the other documents that say MFA is required,
      with the 12-hour rule as "signed in within the last 12 hours" (A143). (R19, R20, R21, R22, R23)
- [ ] The app is still Grow2Notes, with no parent company name, ID, email, IP or secret in the repository and no AI
      feature for note-writers. (R33)
- [ ] Local checks were compile and lint only, the tests are written and CI is green. If PR #211 merged first the
      branch is rebased onto it and keeps both changes. One branch and one pull request, titled as a Conventional
      Commit, with T42 and the story ids in the description, and the by-hand checks are on
      ops/first-use-in-test.md and hold nothing open. (R32, R34, R35)
      Check: the automated tests the T42 plan lists and Build and test on the pull request.

### Notes
Planned on 1 November 2026. The passkey audit on a credential of another account is written on that credential's
account, as POST /api/auth/passkey does today.
