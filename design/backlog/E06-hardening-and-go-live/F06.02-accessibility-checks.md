# F06.02 Accessibility checks

**Outcome:** the finished app is checked as a whole, on real phones and laptops, for WCAG 2.2 AA (A32): automated axe
checks and keyboard-only use on every screen, the visual checks in foundations.md, VoiceOver and TalkBack on the note
form and the Report screen, and the button words with real workers
([design.md §14 M6](../../design.md#m6-hardening-and-go-live)).

## Stories
- S06.02.01 axe and keyboard-only pass on every screen
- S06.02.02 Zoom, text size and contrast checks
- S06.02.03 VoiceOver and TalkBack on the note form
- S06.02.04 VoiceOver and TalkBack on the Report screen
- S06.02.05 Button words checked with five workers

## Feature checks
This feature owns this row in [coverage.md](../coverage.md) (E06). It is linked, not copied:
- design.md §14 M6 *Scope*: **Accessibility** (axe checks, keyboard-only use, and VoiceOver and TalkBack on the note
  form and the Report screen).

Each story checks the release candidate in the test environment. A failure is fixed in that story or filed as a `bug`
under the feature it affects. The per-story accessibility checks in the Definition of Done still apply to every
fix ([README §9](../README.md#9-definition-of-done)).

Enabler: one axe run and one keyboard-only run across the whole finished app. So that problems that only show when
screens are used together, such as focus after moving between screens, are found before go-live.

### Acceptance criteria
Already specified elsewhere (linked, not copied):
- Each screen file's *Accessibility checklist* and its axe criteria (the 13 screens listed in
  [ux/README.md › Screens](../../ux/README.md#screens)).
- [design.md §4.13](../../design.md#413-key-flows): the key flows.
- [foundations.md](../../ux/components/foundations.md) *Implementation notes* › *Manual test list (add to M6's
  accessibility pass)*: item 8 (keyboard only on a laptop).

Specific to this story:
- [x] Playwright with axe runs on every screen in every state its acceptance criteria name, against the release
      candidate in the test environment, with no violations.
- [x] Each key flow in §4.13 is completed on a laptop with the keyboard only: every stop has a visible focus ring, there
      is no trap, and focus lands as the app-shell focus rule says after each screen change. The result is recorded
      per flow.

### Notes
- Done in T26 (24 October 2026), on green CI. The design.md A98 decision: the Playwright run in CI is the evidence for
  "the release candidate in the test environment" (the run on the pull request tests the pull request's build, and the
  run on the push to `main` the build that is deployed to test), and one automated keyboard-only run of each flow at
  1280x800 in Chromium meets "on a laptop with the keyboard only"; a person's own laptop pass is
  ops/first-use-in-test.md step 143, which holds nothing open.
- First criterion: every screen's state list passes axe, and each screen's own spec also calls
  `expectFoundationsToPass` (tests/e2e/foundations.ts) and, through `expectAxeToPass`, proves no sideways scroll at
  320 px in every state. CI run 40107581139 on pull request #134 passed at commit bcadaad, whose last code commit is
  "test(a11y): put the window and scroll back after the 320 px check"; the run on the commit that carries these Notes
  cannot be known when they are written.
- Second criterion: `tests/e2e/key-flows.spec.ts`, one `test.step` for each flow of §4.13, named as the section
  names it, so the CI report has the result for each flow, in the same run. Every stop shows a ring, nothing traps
  focus and focus lands as the app-shell rule says, as `tabTo` and `expectFocusAt` assert.
- The audit additions per screen, the faults found and the readability result are in [tasks.md](../tasks.md) T26's
  Notes.

Enabler: the manual visual checks the UX specs set aside for the M6 accessibility pass, and the one-off go-live
device check of passkey setup from phone email apps. So that people with low vision, large text settings or contrast
themes, and workers outdoors on a phone, can use every screen, and the managers know which email apps staff can set
up a passkey from.

### Acceptance criteria
Already specified elsewhere (linked, not copied):
- [foundations.md](../../ux/components/foundations.md) *Implementation notes* › *Manual test list (add to M6's
  accessibility pass)*: items 1 to 7 (item 8, keyboard only, is in S06.02.01).
- [note-form.md › Accessibility checklist](../../ux/screens/note-form.md#accessibility-checklist) › *Manual test
  passes (M6)*: Windows contrast theme, 200% and 400% zoom, landscape phone and the outdoor daylight check.
- [status-tags.md](../../ux/components/status-tags.md) *Tensions with decisions*: tag borders watched in forced colours.
- [sign-in.md](../../ux/screens/sign-in.md) › Acceptance criteria › Layout and accessibility: the go-live device check
  ("On a real iPhone and Android phone, setup from Gmail, Outlook and the built-in mail app is tried…").

Specific to this story:
- [ ] Each item is checked on a real iPhone, a real Android phone and a laptop, and the result is recorded per item
      and device.
- [ ] The go-live device check is a by-hand step on ops/first-use-in-test.md that holds nothing open (owner, 20 October
      2026, D90): it is done in the test environment with made-up accounts (A35), and each email app's in-app browser
      passkey result is recorded here, per phone.

### Notes
- T26 (24 October 2026) checks in CI what a browser can: the text sizes and zoom sizes as real geometry (320x800,
  320x200 and 640x400, with 200% text and WCAG 1.4.12 spacing), forced colours, 7:1 text, nothing moving and nothing
  pinned (`expectFoundationsToPass`, tests/README.md). Both criteria above need a real iPhone, a real Android phone
  and a person, so they stay unticked and the story is done on the rule that by-hand checks do not hold a story open
  (README §9). They are proven when ops/first-use-in-test.md steps 143 to 147 are run (the section *Accessibility pass
  on the finished app*, whose order paragraph also cites steps 20 to 25 and the device and screen-reader steps of the
  screens) and recorded per item and device in [tasks.md](../tasks.md) T26's Notes. Whether the by-hand checks hold
  go-live is owner question Q12, open, and affects T28 only.

Specific to this story:

      the 1-second check described in guided-notes-textarea.md *Behaviour* item 6 is added in this story;
