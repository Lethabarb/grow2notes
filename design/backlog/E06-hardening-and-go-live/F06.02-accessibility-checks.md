# F06.02 Accessibility checks

**Outcome:** the finished app is checked as a whole, on real phones and laptops, for WCAG 2.2 AA (A32): automated axe
checks and keyboard-only use on every screen, the visual checks in foundations.md, VoiceOver and TalkBack on the note
form and the Report screen, and the button words with real workers
([design.md §14 M6](../../design.md#m6-hardening-and-go-live)).

## Stories
- S06.02.01 axe and keyboard-only pass on every screen
- S06.02.02 Zoom, text size and contrast checks
- S06.02.03 VoiceOver and TalkBack on the note form
- S06.02.04 VoiceOver and TalkBack on the Report screen
- S06.02.05 Button words checked with five workers

## Feature checks
This feature owns this row in [coverage.md](../coverage.md) (E06). It is linked, not copied:
- design.md §14 M6 *Scope*: **Accessibility** (axe checks, keyboard-only use, and VoiceOver and TalkBack on the note
  form and the Report screen).

Each story checks the release candidate in the test environment. A failure is fixed in that story or filed as a `bug`
under the feature it affects. The per-story accessibility checks in the Definition of Done still apply to every
fix ([README §9](../README.md#9-definition-of-done)).

- [ ] Playwright with axe runs on every screen in every state its acceptance criteria name, against the release
      candidate in the test environment, with no violations.
- [ ] Each key flow in §4.13 is completed on a laptop with the keyboard only: every stop has a visible focus ring, there
      is no trap, and focus lands as the app-shell focus rule says after each screen change. The result is recorded
      per flow.

- [sign-in.md](../../ux/screens/sign-in.md) › Acceptance criteria › Layout and accessibility: the go-live device check

Specific to this story:

      and device.
- [ ] The go-live device check is done in the test environment with made-up accounts (A35), and each email app's

- [note-form.md › Accessibility checklist](../../ux/screens/note-form.md#accessibility-checklist) › *Manual test

  M6 pass, with the title read once.
- [guided-notes-textarea.md](../../ux/components/guided-notes-textarea.md) *Accessibility*: the empty-error state with
  both a description and a placeholder.
- [empty-loading-error.md](../../ux/components/empty-loading-error.md) *Implementation notes*: the manual
  VoiceOver and TalkBack check of loading, error and retry on the note form.

Specific to this story:
- [ ] Runs on VoiceOver with iOS Safari and TalkBack with Android Chrome, and NVDA with Chrome as note-form.md lists;
      the result of each item is recorded per screen reader and browser.
- [ ] Dragon and Windows voice typing are tried in Guided notes. If either changes the text without an `input` event,
      the 1-second check described in guided-notes-textarea.md *Behaviour* item 6 is added in this story;
      otherwise it is not added.

```yaml

```

Enabler: the words check that microcopy.md asks for before go-live. So that workers, including those who write in
English as an additional language, know what each main button will do before they press it (A32: plain-English
labels).

### Acceptance criteria
Already specified elsewhere (linked, not copied):
- [microcopy.md](../../ux/components/microcopy.md) §8 *Testing the words*.

Specific to this story:
- [ ] Five of the provider's workers, including some who write in English as an additional language, each say what
      every primary button will do before pressing it, in the test environment with made-up data (A35).
- [ ] The result per button is recorded. Any button that fewer than 4 of the 5 understood goes to the owner as a
      wording question; no wording changes without the owner's approval.
- [ ] A readability checker is run on the worker-facing strings, as a warning sign only, and its result recorded.

### Notes
- The managers arrange the five workers' time.
