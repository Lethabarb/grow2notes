# F06.01 Security review and hardening

**Outcome:** every response carries the security headers from before the first screen, and before any real data
reaches production the whole app has been reviewed against OWASP ASVS level 2 and scanned with OWASP ZAP, Dependabot
and the rate limits are working, and no high or critical finding is open
([design.md §14 M6](../../design.md#m6-hardening-and-go-live), [§9](../../design.md#9-security--privacy)).

## Stories
- S06.01.01 OWASP ASVS level 2 self-review
- S06.01.02 OWASP ZAP baseline scan
- S06.01.03 Dependabot alerts and weekly updates
- S06.01.04 Security headers and CSP on every response
- S06.01.05 Rate limits

## Feature checks
This feature owns these rows in [coverage.md](../coverage.md) (E06). They are linked, not copied:
- design.md §14 M6 *Scope*: **Security** (ASVS level 2 self-review, ZAP baseline scan, dependency scanning, CSP and
  the other security headers, rate limiting and lockout).
- design.md §14 M6 *Done when*: no high or critical findings are open.

Spanning the stories: every high or critical finding from S06.01.01 to S06.01.05 is either fixed in that story or
filed as a `bug` under the feature it affects ([README §3.2](../README.md#32-story-level-types-and-where-technical-work-goes)),
and the feature is not done while any of them is open. S06.05.02 does not create the provider's organisation in
production until that list is empty.

Parts of the M6 *Security* row are built and tested in E00, and S06.01.01's review checks them again rather than a
story here repeating them: NuGet Audit, `npm audit` and SHA-pinned actions (S00.01.02), and Identity lockout
(S00.04.05). S06.01.04 is placed in the backlog before the first screen, so the
Definition of Done's headers bullet holds from then on; it stays in this feature because M6 owns the headers.


Enabler: the middleware that sets the strict content security policy and the other headers in design.md §9.7 on every
response, with its integration test, built before the first screen. So that every screen is built and checked on real
devices under the production headers from the start, as the Definition of Done's headers bullet says, a script
injection or framing attack has nothing to work with, and the strict policy is proven not to break any screen.

### Acceptance criteria
Already specified elsewhere (linked, not copied):
- [design.md §9.7](../../design.md#97-security-headers-and-csp): the header set, the integration test, and the CSP in
  production and test but not under the Vite dev server.
- [design.md §7.2](../../design.md#72-how-the-spa-is-served): no inline scripts, `assetsInlineLimit: 0`, caching.

Specific to this story:
- [ ] The header test covers every kind of response that exists so far: `index.html` from the fallback route, a hashed
      asset, a JSON API response, an unknown `/api` path (`404`), a `401` and `/healthz`.
- [ ] The built `index.html` and assets contain no inline script or style and no `data:` URI.
- [ ] The Playwright smoke run against the published build reports no CSP violation in the browser console.

### Notes
- Placed in the backlog before the first screen (S00.04.02). Response kinds added later, such as the PDF and Word
  downloads in E04 and E05, join the header test under the Definition of Done's headers bullet. The `blob:` downloads
  under the test environment's CSP are checked on real devices in S04.02.05 and S05.01.04, which depend on this story.
- The stories before it (Sprints 01–03) have no screen; this story's header test covers the response kinds they add.
- S06.01.02's ZAP scan and S06.01.01's review check the headers again on the finished app.

Enabler: the rate limits in design.md §9.9, on ASP.NET Core's built-in rate limiter. So that password and code
guessing is slowed to uselessness, and one misbehaving client or account cannot make the app unavailable to everyone
else.

### Acceptance criteria
Already specified elsewhere (linked, not copied):
- [design.md §9.9](../../design.md#99-rate-limiting-and-lockout): the four limits and `429` with `Retry-After`.
  Identity lockout (5 failed attempts, 15 minutes, A25) is built and tested in S00.04.05.
- The screens' handling of `429` and lockout is in their own criteria: sign-in.md (E00), daily-report.md (E04) and
  record-export.md (S05.01.02).

Specific to this story:
- [ ] Forwarded headers are on, so limits key on the real client IP behind App Service's front end, tested with a
      forwarded address.
- [ ] Each row of the §9.9 table returns `429` with `Retry-After` on the first request over its limit, with a test per
      row.
- [ ] The PDF and Word limit is shared: daily report downloads and record exports together count towards one limit of
      10 a minute per user.
- [ ] Typing steadily in the note form for five minutes, with the 2-second autosave, never reaches the 300-a-minute
      limit.
