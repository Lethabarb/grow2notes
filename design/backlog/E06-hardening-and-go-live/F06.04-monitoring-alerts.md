Enabler: the three production alerts and the operator's action group, in `monitoring.bicep`. So that the operator
(the developer's business, D40) hears about an outage or a run of errors straight away, which is what the app's
error messages rely on (empty-loading-error.md: no error codes on screen because the operator gets error alerts).

### Acceptance criteria
Already specified elsewhere (linked, not copied):
- [design.md §10.1](../../design.md#101-resources-production) Alerts row: HTTP 5xx, health-check failure and DTU
  above 80%, emailed to the developer; these are operations alerts, not app emails.
- [design.md §10.8](../../design.md#108-health-endpoints): production's health check is `/healthz/ready`, which
  includes a database check.

Specific to this story:
- [ ] The three alert rules and the action group are in `monitoring.bicep` and deployed to production.
- [ ] Azure Monitor's test of the action group delivers a sample of each alert to the operator's email.
- [ ] Before go-live, while production has no real use, a deliberate health-check failure (how is settled at sprint
      planning) fires the health-check alert, and the alert resolves when the check passes again.
- [ ] No alert carries participant data: alerts hold resource metrics only (§9.5).
