Enabler: the three production alerts and the operator's action group, in the infrastructure definitions. So that the operator
(the developer's business, D40) hears about an outage or a run of errors straight away, which is what the app's
error messages rely on (empty-loading-error.md: no error codes on screen because the operator gets error alerts).

### Acceptance criteria
Already specified elsewhere (linked, not copied):
- [design.md §10.1](../../design.md#101-resources-production) Alerts row: HTTP 5xx, health-check failure and DTU
  above 80%, emailed to the developer; these are operations alerts, not app emails.
- [design.md §10.8](../../design.md#108-health-endpoints): production's health check is `/healthz/ready`, which
  includes a database check.

Specific to this story:
- [ ] The three alert rules and the action group are in the infrastructure definitions (`modules/alerts.bicep` for the
      three alerts, `monitoring.bicep` for the action group) and deployed to production.
- [ ] Azure Monitor's test of the action group delivers a sample of each alert to the operator's email.
- [ ] Before go-live, while production has no real use, a deliberate health-check failure (how is settled at sprint
      planning) fires the health-check alert, and the alert resolves when the check passes again.
- [ ] No alert carries participant data: alerts hold resource metrics only (§9.5).

### Notes
- 25 October 2026 (T22; the first criterion is amended): the alerts are in `modules/alerts.bicep`, which `main.bicep`
  deploys in production only, after the web app. The action group `ag-grow2notes-<env>` stays in `monitoring.bicep`.
  A module of their own avoids a cycle, because the web app already depends on `monitoring.bicep`.
- Thresholds, where design.md §10.1 was silent (T22's Notes in [tasks.md](../tasks.md)): HTTP 5xx, any in
  5 minutes; health check, average below 50% over 15 minutes; DTU, average above 80% over 15 minutes. Each is evaluated
  every 5 minutes and resolves by itself, and all hold resource metrics only, which the fourth criterion asks for.
- The third criterion's method, settled at T22's plan: delete the SQL server's virtual network rule `app-subnet` and
  restart the web app, wait at least 25 minutes for the health-check alert, recreate the rule (or re-run the last
  production Deploy), and see the alert resolve. `ops/go-live.md` C has the steps.
- All four criteria need the production environment, so they stay unticked, with `ops/go-live.md` C as the by-hand
  step. The story is done under README §9, because by-hand checks hold nothing open (D90).
