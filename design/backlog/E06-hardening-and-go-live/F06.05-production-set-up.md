# F06.05 Production set-up

**Outcome:** production runs in Azure Australia Southeast exactly as designed, the provider's organisation exists in
it with its first manager, and the managers can enter the configuration from the current Word template: its prompts
become the guide prompts and its standard tick items become the common items, sorted into groups
([design.md §14 M6](../../design.md#m6-hardening-and-go-live) *Set-up*).

## Stories
- S06.05.01 Production environment ready and checked
- S06.05.02 Provider's organisation and first manager in production

## Feature checks
This feature owns this row in [coverage.md](../coverage.md) (E06). It is linked, not copied:
- design.md §14 M6 *Scope*: **Set-up** (production configuration entered from the current Word template).

The data entry itself is done by the managers, not the developer, and is tracked as the go-live checklist line
"entered by one manager and checked by another" in F06.06. This feature is done when that line has its evidence.

Enabler: the check of production against design.md §10.1 before any real data goes in: every resource row recorded
in `ops/`, the database roles that `sql/grant-identities.sql` set, and the production email records. So that real
participant data only ever goes into an environment that matches the design: in Victoria, locked against deletion,
served at its default Azure host (D91), with one long-lived secret, the Resend key, kept only in Key Vault (D92).

### Acceptance criteria
Already specified elsewhere (linked, not copied):
- [design.md §10.1](../../design.md#101-resources-production): every resource row and its settings.
- [design.md §10.5](../../design.md#105-infrastructure-as-code-bicep): `sql/grant-identities.sql`.

Specific to this story:
- [ ] Each row of the §10.1 table is checked in the production subscription and the result recorded in `ops/`,
      including the `CanNotDelete` lock, FTP and basic-auth publishing off, the federated credential trusting only
      `environment:prod`, and Defender for Cloud's free posture checks.
- [ ] In the production database, the app identity is a member of `grow2notes_runtime` and of no other role, and the
      deployment identity is a member of `db_owner` (`sql/grant-identities.sql`).
- [ ] Production is served at `app-grow2notes-prod.azurewebsites.net` over App Service's certificate, and `App__Origin`
      is that host, fixed before anyone enrols a passkey in production (D91).
- [ ] A test message from the production email sender, sent through Resend from the owner's verified domain with
      tracking off, passes SPF, DKIM and DMARC (D92).

### Notes
- Production itself is built in E00 (M0 scope): `prod.bicepparam`, its identities, the domain, the `prod` environment
  restricted to `main`, `grant-identities.sql` and the database lock in S00.02.04; Azure Policy, the budget and
  Defender in S00.02.01. This story checks them; it does not rebuild them.
- 25 October 2026 (T22; the third and fourth criteria are amended, the enabler text is reworded, D91, D92): there is no
  product domain, DNS record or managed certificate, because production uses the default Azure host. The fourth
  criterion's data-location clause (Communication Services' Australian location) is dropped, because Resend does not
  process email in Australia; design.md A102 and `ops/go-live.md` D have the owner confirm Resend's region, its
  retention of sent content and the privacy and hosting-agreement wording instead.
- 25 October 2026 (T22): all four criteria need the production environment. The first and second are
  `ops/go-live.md` B, the third is B and the first production enrolment (T27), and the fourth is D at T27's first
  invite, because the first invite needs the first manager (S06.05.02). They stay unticked, and the story is done under
  README §9, because by-hand checks hold nothing open (D90).
- 25 October 2026 (T22): S06.05.02's third criterion says the first manager receives the setup email "from the product
  domain". The sender is now the owner's verified Resend domain (A100), not a product domain. Flagged for that story's
  refinement, together with its existing Note that `admin bootstrap` sends no email.

Enabler: `admin bootstrap` run once in production for the provider. So that the provider's first manager can sign in,
invite the other staff and enter the configuration from the Word template.

### Acceptance criteria
Already specified elsewhere (linked, not copied):
- [design.md §7.4](../../design.md#74-operator-commands) `admin bootstrap`: creates the organisation with its Every
  note group (A43) and the first manager's invite, prints the setup link, and writes `admin.bootstrap`.

Specific to this story:
- [ ] Before `admin bootstrap` runs, F06.01's list of high and critical findings is empty (design.md §14 M6 *Done
      when*, D1): no real personal information enters production before the security review, the ZAP scan and the
      rate limits are done.
- [ ] The organisation is created with the provider's name (A1), and that name is checked by hand for the parent
      company's name, as review checks every change to the app (D42, D72).
- [ ] The first manager receives the setup email from the product domain, with no participant data and only the name
      Grow2Notes (D42, A23), and completes setup with MFA on their own phone.
- [ ] The first manager can reach the Manage screens, and the Every note group is on the Common items screen.

### Notes
- After this, the managers invite the staff and enter the participants, goals, common items in groups and guide
  prompts; the checking manager previews the prompts as settings-textarea.md *Per-screen notes* describes. Both are
  go-live checklist lines in F06.06.
- Carried from S00.03.05 on 9 October 2026: `admin bootstrap` prints the first manager's setup link on the SSH
  console and sends no email (design.md §7.4; `ops/break-glass.md`, *admin bootstrap*). So the third criterion's
  "receives the setup email" is settled at this story's refinement, either by changing the criterion or by choosing
  how the operator gets the printed link to the first manager, directly and to no one else, since whoever opens it
  can set up the account.
