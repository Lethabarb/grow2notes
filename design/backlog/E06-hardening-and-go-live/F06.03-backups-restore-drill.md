# F06.03 Backups and restore drill

**Outcome:** production keeps 35 days of point-in-time restore and monthly long-term backups for 12 months, all in
Australian regions, and the operator has a written, repeatable restore drill
([design.md §10.7](../../design.md#107-backups-and-tested-restore-a36), A36).

## Stories
- S06.03.01 Backup retention set and checked in production
- S06.03.02 Restore drill runbook

## Feature checks
This feature owns this row in [coverage.md](../coverage.md) (E06). It is linked, not copied:
- design.md §14 M6 *Scope*: **Backups** (35-day point-in-time restore and monthly long-term backups for 12 months, all
  in Australian regions, A36).

The first restore test of the production backup is a go-live checklist line, so it sits in F06.06 (S06.06.02) and
uses this feature's runbook.

Enabler: the production database's 35-day point-in-time restore and monthly long-term retention, set in Bicep, and
all three backup settings checked against the design. So that any corruption or damage can be undone, from the last
10 minutes back to a year ago, without backups ever leaving Australia.

### Acceptance criteria
Already specified elsewhere (linked, not copied):
- [design.md §10.1](../../design.md#101-resources-production) Azure SQL database row, and
  [§10.7](../../design.md#107-backups-and-tested-restore-a36) *Automatic Azure SQL backups* and *Long-term retention*.

Specific to this story:
- [ ] `sql.bicep` sets, for production, point-in-time restore of 35 days and long-term retention of monthly backups
      for 12 months; `what-if` shows no drift after deploy.
- [ ] A read-only check with the Azure CLI confirms those two settings and the geo-redundant backup storage on the
      production database, and the output is recorded in `ops/`.

### Notes
- Geo-redundant backup storage is set in `prod.bicepparam` by S00.02.04, and Azure Policy *Allowed locations* by
  S00.02.01. This story checks the first and does not repeat the second.

Enabler: `ops/restore-drill.md`, `ops/restore-check.sql` and `ops/restore-log.md`. So that a restore is a rehearsed,
recorded routine, not something worked out during an outage, and the quarterly and yearly drills in §10.9 can be run
the same way each time.

### Acceptance criteria
Already specified elsewhere (linked, not copied):
- [design.md §10.7](../../design.md#107-backups-and-tested-restore-a36) *Restore drill* (quarterly, after a large
  migration, and yearly geo-restore) and *Targets* (RPO 10 minutes or less, RTO 4 hours or less).
- [design.md §10.6](../../design.md#106-database-migrations) *Rollback*: restore to the time recorded before a
  migration ([§10.4](../../design.md#104-cicd-with-github-actions) deploy step 3).

Specific to this story:
- [ ] `ops/restore-check.sql` reports row counts per table, the latest version and audit timestamps, and runs
      `DBCC CHECKDB`; it is read-only.
- [ ] The runbook explains how to open a known note and its versions in the restored copy with a query as the Entra
      admin (§9.4), because restored production data is never attached to the test environment or any app.
- [ ] It covers the quarterly point-in-time drill, the yearly geo-restore into a temporary server in Australia
      Southeast, the restore after a failed migration, and the outage of Australia Southeast (geo-restore into
      Australia East and a Bicep redeploy). Both drills end by deleting the restored copy.
- [ ] `ops/restore-log.md` has a row format for date, restore point, result, time taken and who ran it.
