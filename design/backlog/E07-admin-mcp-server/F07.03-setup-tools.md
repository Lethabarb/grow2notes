# F07.03 Setup tools

**Outcome:** a manager or support person can ask an approved assistant to add or correct a participant; add, reword,
reorder, archive or restore goals, common item groups and common items; or replace the guide prompts. Each tool calls
the same handler as the matching `/api/admin` endpoint, with the same rules, version checks and audit events as the
Manage screens (D48, D59, [mcp-server.md §5.2](../../mcp-server.md#52-tool-list) tools 6, 7 and 10 to 25,
[§5.4](../../mcp-server.md#54-notes-per-tool-area)).

`archive_participant` and `restore_participant` (tools 8 and 9) are delivered in F07.04, because archiving a
participant always needs confirmation (§5.3, MA6).

For every story in this feature, the tool:
- calls the shared handler with the acting user and the channel `Mcp` (mcp-server.md §3.5 convention 1);
- needs the `expectedVersion` the look-up returned for any change to an existing row, gives `precondition.failed` when
  it is stale, and returns `changed: false` when nothing would change (§5.1);
- returns the app's help line on goal, group, item and guide prompt changes (§5.1, design.md §4.8);
- refuses with the codes in §5.5, with field messages worded as in the app and never echoing the value;
- has its row in the tool matrix and the `tools/list` snapshot, and writes its app event with `"via": "mcp"`
  (Definition of Done);
- returns no note content (D49); covered by the canary in S07.02.07.

As a manager or support person, I want my assistant to add a goal for a participant or reword one, so that each

### Acceptance criteria
Already specified elsewhere (linked, not copied):
- [mcp-server.md §5.2](../../mcp-server.md#52-tool-list) rows 10 and 11; §5.4 *Participants and goals*, third bullet;
  §5.5, the `participant.archived` row; §4.8, "an archived participant is read-only".

Specific to this story:
- [ ] `add_goal` adds the goal at the end of the active goals.
- [ ] The shared participant and goal handlers refuse, for an archived participant, a change to its details and the
      adding, rewording, reordering, archiving and restoring of its goals; nothing changes. Release 1 has no such
      refusal on the server (its archived page is read-only on screen only), so this story adds it, once, for both
      channels (mcp-server.md §3.5 convention 1).
- [ ] Given an archived participant, when either tool is called, then `participant.archived` and nothing changes.
- [ ] Goal text over 200 characters gives `validation.failed` with the app's message (A6).
- [ ] design.md §6.9 gains the refusal's code for the app's endpoints, with a decisions.md entry (Definition of Done,
      *Docs*).
