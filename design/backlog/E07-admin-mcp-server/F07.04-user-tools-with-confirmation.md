# F07.04 User tools with confirmation

**Outcome:** a manager or support person can ask an approved assistant to invite a user, reset a sign-in or resend an
invite, deactivate a user, or archive or restore a participant. The four access-related changes never act on the first
call: the person confirms through the assistant's own confirmation form where it has one, or through a preview and then
`confirm: true` where it does not. Support can act only for workers and always gives a reason (D58, MA6, MA7,
[mcp-server.md §5.3](../../mcp-server.md#53-confirmation-for-the-four-access-related-tools)).

Every user tool calls the same handler as the Users screen, so the app's own rules apply: one account per email (A27),
the last-manager rule (A26) and the setup-link emails (A23). Every tool in this feature returns no note content (D49);
covered by the canary in S07.02.07.

### Acceptance criteria
Already specified elsewhere (linked, not copied):
- [mcp-server.md §5.3](../../mcp-server.md#53-confirmation-for-the-four-access-related-tools) point 2 and the preview
  example; §5.5 `precondition.required`.

- [x] Called without `confirm: true`, a confirming tool changes nothing and returns a `status: "preview"` result with

      (`DeactivateUserToolTests.The_preview_names_the_account_and_its_version_and_changes_nothing`, and
      `ToolConfirmationTests.A_client_of_the_old_revision_is_given_the_preview_and_confirms_with_the_version` for the
      mechanism.)

      `precondition.required`.

- [x] The server keeps no state between the two calls.
      (`DeactivateUserToolTests.Confirming_with_the_current_version_deactivates_without_an_earlier_preview`: the
      confirming call needs no earlier one. Nothing is stored; A136.)
- [x] A client that declares no elicitation, or only URL-mode elicitation, gets this path.
      (`DeactivateUserToolTests.A_2026_client_without_form_elicitation_is_given_the_preview` and
      `ToolConfirmationTests.A_client_without_form_elicitation_is_given_the_preview_and_never_a_form`.)

### Notes
- The mechanism is proved with a confirming tool that exists only in the test project, before the four real tools
  arrive.
- 29 October 2026 (T36): done with `deactivate_user`, the first real confirming tool. `ToolConfirmation` is the shared
  mechanism, which `invite_user`, `reset_user_sign_in` and `archive_participant` reuse unchanged (S07.04.03,
  S07.04.04, S07.04.06). It is proved by the test-only `probe_confirm` tool (`ToolConfirmationTests`) and by
  `deactivate_user`. A137 records that an account already in the requested state answers `changed: false` before any
  preview, so such a call needs neither `confirm` nor a version. The sprint is left blank, as for every other done
  story of this epic.

Enabler: the confirmation form in mcp-server.md §5.3 point 1 (form-mode elicitation through a multi round-trip
request), with a protected `requestState`. So that, with an assistant that shows forms, the person answers in the
assistant's app and the model cannot confirm by itself through the tool's arguments.

### Acceptance criteria
Already specified elsewhere (linked, not copied):
- [mcp-server.md §5.3](../../mcp-server.md#53-confirmation-for-the-four-access-related-tools) point 1 and the form
  example; §5.5, the declined result.
- §10 item 8, second bullet, for the mechanism.

Specific to this story:
- [x] Given a client that declares form-mode elicitation, when a confirming tool is called, even with `confirm: true`,
      then it returns an `InputRequiredResult` with one `elicitation/create` form and changes nothing.
      (`DeactivateUserToolTests.A_client_that_shows_forms_is_asked_by_one_even_when_it_sent_confirm_true` and
      `ToolConfirmationTests.A_client_that_shows_forms_is_asked_by_one_even_when_it_sent_confirm_true`, for `form` and
      for a blank `elicitation`.)
- [x] `requestState` is protected with the Data Protection key ring and binds the user ID, the organisation, the
      tool, a digest of the arguments, the row's `expectedVersion` and a 5-minute expiry. State that was tampered
      with, has expired, or is from another user, tool or set of arguments is refused with `precondition.failed`.
      (`DeactivateUserToolTests.A_state_that_is_not_for_the_call_is_refused_and_changes_nothing`,
      `ToolConfirmationTests.A_state_that_is_not_for_this_call_is_refused`,
      `A_state_answered_at_exactly_five_minutes_is_live_and_one_second_later_is_not` and
      `A_state_that_one_tool_asked_is_refused_by_another_tool_for_the_same_arguments`.)
- [x] A retry with `accept` and yes acts. `decline`, `cancel`, or `accept` with no returns `status: "declined"` and
      "Nothing was changed.". A row changed in between gives `precondition.failed`.
      (`DeactivateUserToolTests.Accepting_the_form_deactivates_with_the_version_from_the_state`,
      `Any_answer_but_an_accepted_true_declines_and_changes_nothing`,
      `A_row_that_changed_between_the_form_and_the_answer_is_refused_as_a_changed_account`, and the two tests with an
      SDK client that has an elicitation handler.)
- [x] The form is sent only to a client that declared form mode on that request; a client on an earlier protocol
      revision gets S07.04.01's path (§3.6).
      (`DeactivateUserToolTests.A_2025_client_with_a_form_handler_is_given_the_preview_and_never_asked` and
      `A_2026_client_without_form_elicitation_is_given_the_preview`.)

### Notes
- The form's message uses the same preview wording (P) as S07.04.01.
- 29 October 2026 (T36): done. A136 records the rules: the form is used when `IsMrtrSupported` is true and the
  request's own `_meta` capabilities declare form elicitation (a blank `elicitation` counts); `confirm` and
  `expectedVersion` are ignored on the form path; only `accept` with JSON `true` acts; the state is not single use and
  lives 5 minutes, inclusive; a cross-tool replay is refused. Any answer but a yes, not only `decline`, `cancel` and
  `accept` with no, gives `declined`. The form is audited with one `mcp.read` row by `McpAuditFilter`. A client that
  lets the model write the answer defeats the form, which is MA6's accepted trust boundary.

As a manager or support person, I want my assistant to invite a new worker (and, for a manager, a new manager), so

### Acceptance criteria
Already specified elsewhere (linked, not copied):
- design.md §4.11 *Invite user* and §8.1 steps 1 and 2: the invite and its setup email are the app's own.
- [mcp-server.md §5.3](../../mcp-server.md#53-confirmation-for-the-four-access-related-tools), the *Invite* wording

- §10 item 1, the named `invite_user` cases; §10 item 8 for this tool.

Specific to this story:
- [ ] The invite is the same as one from the Users screen: the same handler, checks, setup email and `user.invited`
      entry, plus `via`, `client`, `tool` and, for Support, `reason`.
- [ ] Given a Support account, when it invites a worker with a reason and confirms, then the invite is made. Without
      a reason, it gets `reason.required`; with role `manager`, it gets `role.not_allowed`. Neither creates anything.
- [ ] Given a manager changed to Support in the app, still holding a token issued while a manager, when it invites
      role `manager`, then `role.not_allowed` on that call.
- [ ] Any role other than `worker` or `manager`, Support included, gives `role.not_allowed`: nobody grants Support
      through MCP (§1.3).
- [ ] An email that already has an account gives `user.email_in_use` (A27).
- [ ] The tool is annotated open-world and not destructive.
- [ ] No tool edits a user's name, email or role, or reactivates a user: `tools/list` has none (MA12).
