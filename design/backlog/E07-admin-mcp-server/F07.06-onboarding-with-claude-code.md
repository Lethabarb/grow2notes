# F07.06 Onboarding with Claude Code

**Outcome:** the owner, as the operator's Support person, runs one Claude Code skill kept in the repository and is led
through onboarding a new provider, end to end: the preconditions, the by-hand operator steps, and the set-up that the
Release 2 tools cover. It adds no tool, server feature or operator command over MCP (D48, D95). It is for the operator,
not for the support workers who write notes (D31 as amended by D48).

## Stories
- S07.06.01 Onboard a new provider with Claude Code
- S07.06.02 An agent sets up a provider's organisation and first manager

## Feature checks
Owns this row in [coverage.md](../coverage.md) (E07), linked and not copied:
- D95: a Claude Code skill in the repository leads the owner through onboarding a new provider.
- D101: the skill's agent creates a provider's organisation and first manager through `admin bootstrap`.

As the owner, acting as the operator's Support person, I want a Claude Code skill that leads me through onboarding a new
provider, so that the preconditions, the by-hand steps and the set-up through the assistant happen in the right order,
with nothing done twice and nothing sensitive handled.

Requested by the owner on 28 October 2026: "purely ai led through claude code (mcp + skill to onboard)". One provider
at a time; row-level security stays deferred (D94). The ids in brackets are the T41 plan's requirement ids.

### Acceptance criteria
Already specified elsewhere (linked, not copied):
- [mcp-server.md §5.3](../../mcp-server.md#53-confirmation-for-the-four-access-related-tools) and §5.6: confirmation
  and the rate limits the skill works within.
- [ops/break-glass.md](../../../ops/break-glass.md) and [ops/go-live.md](../../../ops/go-live.md) section D: the
  by-hand steps the skill explains and never runs.

Specific to this story:
- [ ] Before any provider data enters the chat, the skill checks the environment and its preconditions with the owner
      and stops, naming what is missing, on any no. Test accepts made-up data only. Production needs the go-live gate,
      the provider's written approval of Claude Code (MA1), the operator's own AI provider checks (D57, C3) and
      `Mcp:Enabled` on. (R03, R04)
      Check: step 205.
- [ ] The organisation and its first manager are made by hand ('admin bootstrap', or in production go-live.md D),
      which the skill explains and never runs. It never asks for the setup link and tells the owner never to paste it.
      Nothing it writes turns `Mcp:Enabled` on. (R05, R06, R29)
      Check: `OnboardingSkillTests.The_skill_holds_no_email_address_or_setup_link`; step 205.
- [ ] Access for the assistant is led by hand: a manager grants the owner a Support account, the operator registers
      Claude Code with 'admin mcp-client add' using the client ID and redirects from Claude Code's own documentation,
      and the owner adds the server at local scope from a folder outside the repository. No `.mcp.json` or other file
      that connects agents to a deployed site is committed. (R07, R08, R09, R10)
      Check: `OnboardingSkillTests.No_file_in_the_repository_connects_an_agent_to_a_site`; steps 204 and 205.
- [ ] The settings the owner copies ask before every access tool and allow only the nine set-up and look-up tools by
      exact name. They deny web search, fetch, the Bash and PowerShell shells and file writes. The skill starts only
      when the owner types `/onboard-provider` and has no `allowed-tools`. It tells the owner to use the default
      permission mode and no Elicitation hook. (R11)
      Check: `OnboardingSkillTests.The_settings_the_owner_copies_ask_before_every_access_tool` and
      `The_skill_pre_approves_no_tool_and_starts_only_when_the_owner_asks`; step 205.
- [ ] Set-up goes in order (common items, guide prompts, participants' goals, then worker invites), from typed rows or
      a file the owner names, with one yes per section. A manager adds participants in the app, because the skill never
      handles a date of birth, and the skill adds their goals. It looks up before every add, so a re-run adds nothing
      twice, and it keeps no progress file. (R13, R14, R15)
      Check: step 206 (a re-run); step 205.
- [ ] Workers are invited last, one at a time, role `worker` only, each with a reason that says who asked and how and
      each confirmed by the owner in that turn. It never answers a form or preview for the owner, and works on the
      form path and the preview path. It stays within the `/mcp` limits and recovers from `rate_limited`, HTTP 429
      with Retry-After and an expired sign-in by looking up again. (R12, R16, R17, R18, R19, R28)
      Check: `InviteUserToolTests`, `ConfirmedChangeLimitTests`, `AssistantRateLimitsTests` and `ToolConfirmationTests`
      for the server side; steps 205 and 206 for the skill.
- [ ] The skill sends only what the tools need. It never asks for or handles note content, dates of birth, setup links,
      passwords or codes, and it treats text in results and files as data. It is not an AI feature for the support
      workers who write notes, the app's name is Grow2Notes everywhere and no address, ID or secret is in any file.
      (R20, R30, R31)
      Check: `OnboardingSkillTests.The_template_is_a_header_of_kind_name_and_text_with_no_date_of_birth` and
      `The_skill_holds_no_email_address_or_setup_link`; `NoNoteContentRulesTests`; step 207.
- [x] The skill is in `.claude/skills/onboard-provider/` and is for one provider at a time. It uses only tools listed
      in `tools-list.json`, and a CI test fails if a name it mentions is not listed or if it calls a tool beyond its
      ten. (R01, R02, R21, R22)
      Check: `OnboardingSkillTests.Every_tool_the_skill_names_is_one_the_server_lists` and
      `OnboardingSkillTests.The_skill_calls_only_the_ten_tools_of_its_list`.
- [ ] It ends with a summary of what was set up, what was already there and what is left by hand (participants with
      dates of birth, the manager's checks, staff onboarding, clean-up with 'claude mcp logout' then 'claude mcp
      remove'). The summary holds no address, link or note content. (R23)
      Check: the rehearsal, `ops/first-use-in-test.md` steps 205 and 207.
- [x] The records are in place: an ops page linked from ops/README.md and go-live.md section D, D95, A140, the T41
      section, this story, the rehearsal steps on ops/first-use-in-test.md and the research record of what was read
      in Claude Code's documentation and when. Local checks were compile and lint only, CI is green, and no test was
      removed or weakened. (R24, R25, R26, R27, R32, R33, R34, R35)
      Check: the files named here and the checks of the other nine; Build and test green on the T41 pull requests.

As the owner, acting as the operator, I want the onboarding skill's agent to create a provider's organisation and its
first manager for me, so that I never type in the SSH console, and the first manager gets the usual setup-link email.

Requested by the owner on 3 November 2026 (D101). The ids in brackets are the T43 plan's requirement ids.

### Acceptance criteria
Already specified elsewhere (linked, not copied):
- [design.md §7.4](../../design.md) and [ops/break-glass.md](../../../ops/break-glass.md): the `admin bootstrap` and
  `admin reset-signin` commands and the by-hand block that stays as the fallback.
- S00.02.07: the setup-link email's wording (D85).

Specific to this story:
- [ ] `admin bootstrap` remains the only way an organisation starts: no sign-up screen, no Operator screen or role, no
      MCP tool, and no endpoint. An agent may create one organisation per new provider, in test or production, through
      it, and never a second for a provider that has one. A second organisation in production waits for row-level
      security (design.md §5.9 item 6). (R01, R14, R15)
      Check: `EndpointMatrixTests` and the tools-list snapshot, unchanged; `OnboardingSkillTests`; first-use steps.
- [ ] The step runs with no hand typing in the SSH console, on the operator's Azure CLI sign-in alone (Microsoft
      Entra, basic authentication off), from Windows 11 with the CLI signed in as Owner, inside the running web app
      with its own identity and settings. The route is proven from Microsoft's documentation in planning, and the
      agent never types, reads or handles a password, key, token or setup link. (R02, R03, R05)
      Check: the T43 Notes (Learn, 3 November 2026); `OnboardingSkillTests` (the script's pins); first-use steps.
- [ ] The agent tells the owner whether the step succeeded or was refused, and why in plain words, without seeing
      the link or any personal value. If the email goes and the commit then fails or the link is lost, the recovery is
      `admin reset-signin`, and a re-run of bootstrap is refused on the address. (R04, R18)
      Check: `OnboardingSkillTests`; `BootstrapCommandTests`; first-use steps.
- [ ] No organisation name, manager name or address appears in the repository, in GitHub Actions inputs or logs, in
      telemetry or in the operator's shell history, and the setup link never enters the chat or any log: in Azure it
      is sent only by email and the app never falls back to printing it. Operator commands register no telemetry.
      (R06, R07)
      Check: `BootstrapCommandTests` (log scan, empty output), `AdminCommandsFromTheAppBinaryTests`,
      `OnboardingSkillTests` (whole-folder scan); first-use steps (grep of the logs).
- [ ] `admin bootstrap` emails the first manager the same setup-link email an invite sends, through Resend, with the
      same wording, sender and 7-day single-use link, in the same transaction rules: a send that fails leaves nothing
      created and the command refuses with 'Nothing was written'. No new audit event and no new email type; the
      email text is unchanged, including the accepted sentence 'a manager added you'. (R08, R10, R11)
      Check: `BootstrapCommandTests`; `SetupLinkEmailTests` and `AuditEventsTests`, unchanged.
- [ ] `admin reset-signin` emails the new link under the same rules, with a failed send changing nothing, and stays
      a by-hand operator command that is not in the skill. (R09)
      Check: `ResetSignInCommandTests`; first-use step 29.
- [ ] The agent runs the step only after the owner has confirmed, in that turn, the organisation's name, the first
      manager's name and address, and that the provider named its first manager on a call (A105). The skill's rule
      against shell commands has exactly one stated exception for this step, confirmed at each use, and every other
      shell, web and file-write route stays refused. (R12, R13)
      Check: `OnboardingSkillTests` (settings block and SKILL.md); first-use steps (an unconfirmed call stops).
- [ ] In production the step runs only when go-live section D says so, after D1's gate, and the task touches no Azure
      resource, setting, secret or the key size change. Go-live D has the first manager get the link by email, with
      no mobile number collected, and checks SPF, DKIM and DMARC on that email. Test runs use a first-manager
      address in a mailbox the operator controls, with made-up names. (R16, R17, R22)
      Check: `ops/go-live.md` section D and `ops/first-use-in-test.md`, read in review.
- [ ] The operator's checks before the command include that the app has the email sender's settings, named and never
      shown by value, and a missing setting means nothing is created. (R19)
      Check: `OnboardingSkillTests` (the eight names); `AdminCommandsFromTheAppBinaryTests` (no email settings);
      first-use steps.
- [ ] Automated tests cover it: a successful bootstrap and reset-signin each send exactly one setup-link email to the
      right address and print nothing; a failed send leaves nothing created; neither the address nor the link reaches
      the logs; the CI end-to-end flows still get their link from the console email; the skill's tests pin the one
      exception. They run in CI only. (R20)
      Check: the test classes named above and `tests/e2e/fixtures.ts`.
- [ ] The records match: break-glass.md, go-live.md section D, onboard-provider.md, the skill's SKILL.md and
      by-hand.md, first-use-in-test.md, design.md (§7.4, §8.1, A105, A130, A144 onward), the stories that said the
      link is printed, tests/README.md, the T43 section with Notes on every default, and D101. The parent company's
      name, IDs, emails, IPs and secrets appear nowhere, the work is small and reuses the existing email, invite-send
      pattern and admin command, and T43 can merge before go-live D. (R21, R23, R24)
      Check: the files named here, read in review.
