# F07.02 MCP endpoint, look-ups and audit

**Outcome:** an approved assistant with a valid token can call `/mcp` and use the five look-up tools for a manager or
Support person. Every call is checked against the person's current role and status, held to their organisation, and
audited with the assistant that received the data, and the build fails if any tool could return note content (D49,
[mcp-server.md §4.5](../../mcp-server.md#45-checks-on-every-mcp-request),
[§6](../../mcp-server.md#6-data-returned-and-the-no-note-content-guarantee), [§9](../../mcp-server.md#9-audit)).

## Stories
- S07.02.01 MCP endpoint with checks on every request
- S07.02.02 Access ends on the next call
- S07.02.03 Audit every MCP call
- S07.02.04 Look up participants and their goals
- S07.02.05 Look up users, common items and guide prompts
- S07.02.06 Architecture, contract and snapshot rules
- S07.02.07 Canary tests over every tool

## Feature checks
Owns these rows in [coverage.md](../coverage.md) (E07). They are linked, not copied:
- mcp-server.md §10 automated item 1, *Tool matrix* (built here; every later tool adds its row, Definition of Done).
- mcp-server.md §10 automated item 2, *The no-note-content tests*.
- mcp-server.md §10 automated item 3, *Separation of sign-in*.

- MA5 (no date of birth in any result), MA8 (every call audited, naming the assistant) and MA10 (no IP restriction;
  the `Origin` rule; no CORS headers).
- mcp-server.md §1.2 *Users* and §1.2 *Participants*. This feature starts both with the look-ups (`list_users` in
  S07.02.05; `find_participants` and `get_participant` in S07.02.04), so it owns them, as in R1 (coverage.md, *How to

### Notes
- The server instructions are (P). They ship with the proposed wording unless the owner changes it.
- 27 October 2026 (T32): `sprint` is left blank, as for every other done story of this epic. The mechanism differs
  from the plan in two places with the same behaviour. `McpSetup` does not turn on OpenIddict's authorisation-entry
  validation, which checks an authorisation only for a stored token, and an access token here is self-contained.
  `AssistantCallCheck` reads the authorisation itself and answers `invalid_token` with "The connection has ended.",
  a third app string beside the two that the design names. The challenge and the protected resource document come
  from the app, not the SDK (A120), so the challenge for a request with no token has no `error` parameter. T32
  deliberately removed `AuthorisationServerTests.What_a_later_task_adds_is_still_a_404_problem`, which asserted a 404
  for the protected resource document that is now served; the 404 of the address with `/mcp` after it is covered by
  `McpEndpointTests`. No security test was removed or weakened otherwise. The stand-in tools in the test assembly
  (`ProbeTools`) stood in for the tools that T33 now ships (A119). T33 replaced the criterion's test,
  `The_production_setup_lists_no_tools_on_either_revision`, with
  `The_production_setup_lists_the_snapshot_tools_on_either_revision`, because production now lists two tools.

As a manager, I want someone I deactivate, reset or make a worker to lose their assistant's access on its very next

### Acceptance criteria
Already specified elsewhere (linked, not copied):
- [mcp-server.md §4.6](../../mcp-server.md#46-how-access-ends), the rows on deactivation, reset, `admin signout-all`,
  being made a worker and removal of an assistant's registration.
- §10 item 5, all of it.

Specific to this story:
- [x] Deactivate and reset sign-in, from the app or through MCP, and `admin signout-all` revoke the person's (or
      everyone's) OpenIddict authorisations in the same transaction as the security stamp rotation.
      (`AccessEndsTests.The_event_revokes_the_connection_in_its_own_change_so_the_next_call_and_the_refresh_are_refused`,
      rows deactivate, reset sign-in, admin reset-signin and admin signout-all: the authorisations are all revoked
      before any refresh or `/mcp` call. These are the app paths; the through-MCP rows are added by T36 and T37.)
- [x] Given each of those events, a change to worker, or the removal of the assistant's registration, when the
      assistant next calls `/mcp`, then `401`, and its refresh token no longer works.
      (The same theory, with rows made a worker, email changed, signed out on another device and registration
      removed; the refresh answers `invalid_grant`, or `invalid_client` for the removal.)

### Notes
- 27 October 2026 (T32): signing out and an email change also end the person's connections, and `admin signout-all`
  revokes once per person inside its loop (A118). The existing logout, deactivation, reset and sign-out-all tests run
  with the switch off, which shows that the revocation does not break those paths while `Mcp:Enabled` is false.

Enabler: one call-tool filter, `McpAuditFilter`, that audits every MCP call through a write-only `IAuditWriter`, and
the MCP events added to the audit catalogue. So that every disclosure to an AI provider is recorded with the assistant
that received it (C8, MA8), and the provider can answer "what did we disclose, to which AI provider, and when"
(s 26WC).

### Acceptance criteria
Already specified elsewhere (linked, not copied):
- [mcp-server.md §9](../../mcp-server.md#9-audit): the events table and the four bullets under it.
- §6.3 rule 1, the `IAuditWriter` part.
- §10 item 9 (built here; later tools add their events as part of done).

Specific to this story:
- [x] `IAuditWriter` is a write-only interface in its own namespace: no read or query method, and no `AuditEvent` in
      its signatures. Release 1's audit writer (S00.03.03) is reached through it.
      (`AuditWriterTests.IAuditWriter_is_write_only_in_its_own_namespace`.)
- [x] A change through MCP writes the app's own event in the same transaction, with `"via": "mcp"`, `"client"` and
      `"tool"` added to the usual `Details`.
      (`McpAuditTests.A_change_writes_the_app_event_with_via_client_and_tool_and_no_mcp_read` and
      `AuditWriterTests.An_event_written_during_an_mcp_call_carries_via_client_and_tool_and_leaves_the_callers_details_unchanged`.)
- [x] Look-ups, previews and confirmation forms write `mcp.read` with the IDs returned and a count; `ParticipantId`
      is set when exactly one participant was returned.
      (`McpAuditTests.A_look_up_writes_mcp_read_with_the_ids_returned_a_count_the_client_and_the_tool`, with one and
      two participants, and `A_call_aborted_after_the_tool_read_still_writes_mcp_read`. Look-ups and a changed result
      are proven through stand-in tools; previews and confirmation forms are T36's, which joins this test.)
- [x] Every tool error writes `mcp.refused` with `client`, `tool` and `code`, and it is kept although the refused
      change's own transaction rolls back.
      (`McpAuditTests.A_tool_error_writes_mcp_refused_with_the_client_the_tool_and_the_code` and
      `An_exception_in_a_tool_answers_unexpected_rolls_back_writes_mcp_refused_and_logs_no_detail`.)
- [x] `ActorUserId` is the user from the token; `IpAddress` is the address the assistant called from.
      (`McpAuditTests.A_look_up_writes_mcp_read_with_the_ids_returned_a_count_the_client_and_the_tool` reads both
      back.)
- [x] design.md §5.4 gains the MCP events, and the table-driven audit test from S05.02.01 gains a row for each one
      (`mcp.read`, `mcp.refused`, `mcp.authorised`, `mcp.authorisation_refused` and the three `admin.mcp_client_`
      events).
      (`AuditEventsTests.Its_trigger_writes_exactly_one_entry_with_its_fields_and_values` has a row for each of the
      seven; `AuditTypesTests` checks the catalogue against §5.4.)

### Notes
- 9 October 2026, from S00.03.03: `IAuditWriter` saves through the scope's `Grow2NotesDbContext`, and the save is the
  whole context's, so it also writes any change the context still tracks. An event written after a failed change,
  such as `mcp.refused`, is therefore written outside that change's transaction, from a fresh scope or after
  `ChangeTracker.Clear()`; otherwise it would try the failed change again, or roll back with it.
