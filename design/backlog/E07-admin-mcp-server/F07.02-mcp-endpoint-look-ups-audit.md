# F07.02 MCP endpoint, look-ups and audit

**Outcome:** an approved assistant with a valid token can call `/mcp` and use the five look-up tools for a manager or
Support person. Every call is checked against the person's current role and status, held to their organisation, and
audited with the assistant that received the data, and the build fails if any tool could return note content (D49,
[mcp-server.md §4.5](../../mcp-server.md#45-checks-on-every-mcp-request),
[§6](../../mcp-server.md#6-data-returned-and-the-no-note-content-guarantee), [§9](../../mcp-server.md#9-audit)).

## Stories
- S07.02.01 MCP endpoint with checks on every request
- S07.02.02 Access ends on the next call
- S07.02.03 Audit every MCP call
- S07.02.04 Look up participants and their goals
- S07.02.05 Look up users, common items and guide prompts
- S07.02.06 Architecture, contract and snapshot rules
- S07.02.07 Canary tests over every tool

Enabler: `POST /mcp` with the MCP C# SDK 2.x, stateless, behind bearer-only sign-in and steps 1 to 5 of the checks in
mcp-server.md §4.5 (step 6, rate limits, is S07.05.01). So that every tool runs only for an active manager or Support
person of the token's organisation, with the role read from the database on every call.

### Acceptance criteria
Already specified elsewhere (linked, not copied):
- [mcp-server.md §4.5](../../mcp-server.md#45-checks-on-every-mcp-request) steps 1 to 5;
  [§4.2](../../mcp-server.md#42-discovery) *Challenge* and *Protected resource metadata*;
  [§4.7](../../mcp-server.md#47-keeping-the-two-kinds-of-sign-in-apart); §4.8 first bullet (the `McpAdmin` policy);
  §5.5 *Protocol and HTTP errors*.
- §10 item 3, all of it.

Specific to this story:
- [ ] Without a token, `/mcp` returns `401` with the `WWW-Authenticate` header in §4.2. The protected resource
      metadata's `resource` is exactly `https://<domain>/mcp`, and its only authorisation server is the issuer.
- [ ] Given a token for a user since deactivated, reset or made a worker, or whose security stamp changed, when it
      calls `/mcp`, then `401` with `error="invalid_token"`, and that user's OpenIddict authorisations are revoked.
- [ ] Given a manager changed to Support in the app, when their token next calls `/mcp`, then the role claim on that
      call is Support. (S07.04.03 tests this against `invite_user`.)
- [ ] The tenant is set from the token's organisation ID, and the two-organisation test covers `/mcp`.
- [ ] A client on revision 2025-11-25 and one on 2026-07-28 can both list tools; `GET` or `DELETE` from an
      earlier-revision client gets `405` (§3.6, §5.5).
- [ ] The server names itself Grow2Notes and sends the server instructions in §5.1 (P). No description or result
      names the parent company (D42).
- [ ] One error filter turns any exception into the `unexpected` tool result, rolls the transaction back, and sends
      the detail to telemetry by ID only (§5.5, §6.3 rule 5).
- [ ] The SDK's log categories run at `Warning`, and no tool argument, result or token is logged (§8).
- [ ] The MCP server makes no outbound HTTP call and passes no token on (§3.2, §4.7).

### Notes
- The server instructions are (P). They ship with the proposed wording unless the owner changes it.

## S07.02.03 Audit every MCP call

```yaml
id: S07.02.03
type: enabler
title: Audit every MCP call

points: 3
sprint:
depends_on: [S07.02.01]
sources: [MA8, A28, "mcp-server.md §6.3", "mcp-server.md §7.2", "mcp-server.md §7.3", "mcp-server.md §9", "mcp-server.md §10", "design.md §5.3", "design.md §5.4", "design.md §5.8"]
github:
azure:
```

Enabler: one call-tool filter, `McpAuditFilter`, that audits every MCP call through a write-only `IAuditWriter`, and
the MCP events added to the audit catalogue. So that every disclosure to an AI provider is recorded with the assistant
that received it (C8, MA8), and the provider can answer "what did we disclose, to which AI provider, and when"
(s 26WC).

### Acceptance criteria
Already specified elsewhere (linked, not copied):
- [mcp-server.md §9](../../mcp-server.md#9-audit): the events table and the four bullets under it.
- §6.3 rule 1, the `IAuditWriter` part.
- §10 item 9 (built here; later tools add their events as part of done).

Specific to this story:
- [ ] `IAuditWriter` is a write-only interface in its own namespace: no read or query method, and no `AuditEvent` in
      its signatures. Release 1's audit writer (S00.03.03) is reached through it.
- [ ] A change through MCP writes the app's own event in the same transaction, with `"via": "mcp"`, `"client"` and
      `"tool"` added to the usual `Details`.
- [ ] Look-ups, previews and confirmation forms write `mcp.read` with the IDs returned and a count; `ParticipantId`
      is set when exactly one participant was returned.
- [ ] Every tool error writes `mcp.refused` with `client`, `tool` and `code`, and it is kept although the refused
      change's own transaction rolls back.
- [ ] `ActorUserId` is the user from the token; `IpAddress` is the address the assistant called from.
- [ ] design.md §5.4 gains the MCP events, and the table-driven audit test from S05.02.01 gains a row for each one
      (`mcp.read`, `mcp.refused`, `mcp.authorised`, `mcp.authorisation_refused` and the three `admin.mcp_client_`
      events).

### Notes
- 9 October 2026, from S00.03.03: `IAuditWriter` saves through the scope's `Grow2NotesDbContext`, and the save is the
  whole context's, so it also writes any change the context still tracks. An event written after a failed change,
  such as `mcp.refused`, is therefore written outside that change's transaction, from a fresh scope or after
  `ChangeTracker.Clear()`; otherwise it would try the failed change again, or roll back with it.

Already specified elsewhere (linked, not copied):
- [mcp-server.md §5.2](../../mcp-server.md#52-tool-list) rows 2 and 3;

### Acceptance criteria
Already specified elsewhere (linked, not copied):
- [mcp-server.md §6.3](../../mcp-server.md#63-how-the-guarantee-is-enforced-in-code) rule 3.
- §10 item 2 (the canary) and item 11.

Specific to this story:
- [ ] Against the SQL Server test container, a unique canary is written into every note-only text field: draft and
      version narratives, flag reasons and review comments.
- [ ] The test reads `tools/list` and calls every tool with generated valid arguments, and with its previews,
      confirmation forms and error cases once they exist. It fails if a tool has no argument generator.
- [ ] It collects every response body, error and log line, and the telemetry sent to an in-memory sink, and fails if
      the canary appears anywhere.
- [ ] Names, emails and goal wording used in the MCP calls never appear in logs or telemetry (§10 item 11).
