# F07.01 Support role, sign-in and Connect an AI assistant

**Outcome:** managers can give the operator's support person a Support account that sees nothing but sign-in. The
operator registers only the AI assistants the provider has approved in writing. A manager or Support person connects
an approved assistant by signing in with their own account and MFA and choosing Allow on the Connect an AI assistant
screen, and gets tokens that last no longer than an app session
([mcp-server.md §2.2](../../mcp-server.md#22-the-support-role), [§4](../../mcp-server.md#4-authentication-and-authorisation),
[§11.2](../../mcp-server.md#112-registering-an-approved-assistant)).

## Stories
- S07.01.01 Invite a Support account
- S07.01.02 Support sign-in and landing page
- S07.01.03 Spike: OpenIddict settings for approved assistants
- S07.01.04 Authorisation server, off switch and discovery
- S07.01.05 Register an approved assistant

- S07.01.07 Refuse workers and warn about desktop assistants

Question: can OpenIddict 7.7.1 do what [mcp-server.md §4.1–4.2](../../mcp-server.md#41-settings) needs, and where
does it need custom code? Time-box: 5 hours. Output: answers written into mcp-server.md (§4.1 note, §4.2, §10 item 4
and the §13 *Unverified* list), with the two slice 1 choices made and stated.

The questions, all marked unverified in mcp-server.md:
1. Does OpenIddict need a signing key at start-up when every token is protected by Data Protection and no identity
   token is issued?
2. Is `authorization_response_iss_parameter_supported: true` in its discovery document, and is `iss` sent on the
   redirect?
3. How are `client_id_metadata_document_supported: true` and `token_endpoint_auth_methods_supported: ["none"]` added
   to the discovery document, with no `registration_endpoint`?
4. What is its maximum client ID length? Metadata-document URLs are the client IDs.
5. Can a registered loopback redirect URI match on any port, for both `127.0.0.1` and `localhost`?
6. Does 7.7.1 have any metadata-document support of its own? (An issue asking for it was open on 4 October 2026.)
7. What is the refresh-token reuse leeway's current default, and which value should Grow2Notes use?
8. Should a refresh token be issued when a client's registration lists the `refresh_token` grant but it does not ask
   for `offline_access`? (Slice 1 decides, §4.1.)

### Acceptance criteria
- [ ] Each question has an answer with its evidence (documentation, source code or a throwaway test), or is marked
      still unverified with the reason.
- [ ] Choices 7 and 8 are recorded in mcp-server.md §4.1 and §10 item 4.
- [ ] Any gap that needs custom code becomes a criterion in S07.01.04, S07.01.06 or S07.01.08. A gap that can't be
      met at all goes to the owner as a decision question.

Enabler: OpenIddict 7 server and validation inside the app, its four tables, the `Mcp:Enabled` switch and the
authorisation server's discovery document. So that approved assistants can find out how to sign in, and the whole
feature stays off until switch-on (MA11).

### Acceptance criteria
Already specified elsewhere (linked, not copied):
- [mcp-server.md §4.1](../../mcp-server.md#41-settings) rows *Grant*, *Client type*, *Scope* and *Resource and
  audience*; §4.2 *Authorisation server metadata*; §3.1 (the off switch).
- §10 item 4: the discovery document case. §10 item 6: the `Mcp:Enabled = false` case.

Specific to this story:
- [ ] OpenIddict protects its tokens with the app's Data Protection key ring (`UseDataProtection`); no new key,
      certificate or secret is stored, apart from whatever S07.01.03 found a start-up signing key needs.
- [ ] Only the authorisation code grant with PKCE `S256` is enabled: no implicit, password, client credentials or
      device grants.
- [ ] The resource `https://<domain>/mcp` and the scopes `grow2notes.admin` and `offline_access` are registered.
- [ ] A test reads the discovery document and finds `code_challenge_methods_supported: ["S256"]`,
      `authorization_response_iss_parameter_supported: true`, `client_id_metadata_document_supported: true`,
      `token_endpoint_auth_methods_supported: ["none"]`, and no `registration_endpoint`.
- [ ] OpenIddict's four tables arrive in an expand-only migration. The tenant-isolation test lists them as named
      exceptions beside `AspNetUsers` (design.md §5.9), and they hold no participant data.
- [ ] `Mcp:Enabled` is an app setting, `false` by default in every environment and in Bicep. When it is `false`,
      `/mcp`, `/oauth/*`, the consent endpoints and both discovery locations return `404` (test). The test environment
      turns it on for Release 2 work (§11.6).

Enabler: the operator command `admin mcp-client` with `add`, `list` and `remove`. So that only the AI assistants the

location the operator registered (MA1, MA2).

### Acceptance criteria
Already specified elsewhere (linked, not copied):
- [mcp-server.md §11.2](../../mcp-server.md#112-registering-an-approved-assistant), all of it, including every check
  `add --metadata-url` makes on the document.
- §4.3 *The choice*, points 2 to 5.

Specific to this story:
- [ ] `add --metadata-url` fetches the document once, over HTTPS, when the operator runs it. Nothing else in the app
      fetches a metadata document (S07.01.06 tests the sign-in side).
- [ ] Each check in §11.2 has a test with a document that fails it, and the command stores nothing in that case.
- [ ] `add --client-id` stores a public client with the given redirect URIs, each HTTPS or a loopback address, and no

- [ ] Running `add` again for the same client ID updates its name, company, data location and redirect URIs and
      writes `admin.mcp_client_updated`; the first `add` writes `admin.mcp_client_added`.
- [ ] `remove` deletes the registration, revokes its tokens and authorisations in the same transaction, and writes
      `admin.mcp_client_removed`.

- [ ] design.md §7.4 and the operator command runbook list the command (Definition of Done, *Docs*).

### Notes

  records (§11.2). Registration in production is part of S07.05.09.


As a manager or support person, I want to connect an approved AI assistant by signing in to Grow2Notes with my own
account and MFA, and choosing Allow on a screen that says what the assistant can do and where my data goes, so that
the assistant can make admin changes for me.

### Acceptance criteria
Already specified elsewhere (linked, not copied):
- [mcp-server.md §3.4](../../mcp-server.md#34-connecting-an-assistant-the-flow) (the flow);
  [§4.4](../../mcp-server.md#44-sign-in-and-the-connect-an-ai-assistant-screen) steps 1, 2, 4 (managers and Support),
  5 and 6; §4.1 rows *Sign-in*, *Consent* and *Access token*.
- §10 item 4, every case except refresh and revocation (S07.01.08): unknown client refused before sign-in with no
  outbound request; PKCE, redirect URI and `resource` refusals; exact HTTPS and any-port loopback matching; `iss` on
  the redirect; a replayed code; no role claim; client authentication other than `none` refused.
- §10 item 6: the screen's content, and Allow ending at the exact registered redirect URI under the production CSP.

Specific to this story:
- [ ] The consent endpoints carry the Worker, Manager or Support policy from S07.01.02. Workers are answered in
      S07.01.07.
- [ ] The screen's name, company and data location come from the operator's registration; nothing is taken from the
      assistant's own metadata.
- [ ] Given no Grow2Notes session, when the person opens the link from their assistant, then they sign in (passkey, or
      password and 6-digit code) and come back to the same Connect screen. Checked by hand on Safari and Chrome, on a
      phone and a laptop (§4.4 step 2).
- [ ] Given a stored authorise request more than 10 minutes old, when the person chooses Allow, then it is treated as
      an invalid request: no code and no redirect.
- [ ] **Cancel** returns `access_denied` to the registered redirect URI and writes `mcp.authorisation_refused` with
      `why: cancelled`.
- [ ] **Allow** writes `mcp.authorised` with the client and scope. A second connection shows the screen again;
      nothing is remembered (MA4).
- [ ] The token endpoint exchanges the code using the `code_verifier` and `resource`, with no client secret, and
      issues a 10-minute access token with audience exactly `https://<domain>/mcp`. It carries the user ID, the
      organisation ID, the client ID, a hash of the security stamp and `auth_time`, and no role (MA3).
- [ ] A refused authorise request logs the refused client ID (a URL, never personal information), so the operator
      can find an assistant's client ID from one attempt in test (§11.2).

### Notes
- The consent copy is (P). It ships with the proposed wording unless the owner changes it.
- mcp-server.md gives no wording for the invalid-request error page. Use the app's existing general error wording
  from the microcopy glossary; don't write new copy.
- The "no outbound request" check uses a test HTTP handler that fails on any request (§10 item 4).

## S07.01.08 Stay connected within the app's session limits

```yaml
id: S07.01.08
type: story

points: 3
sprint:

github:
azure:
```

As a manager or support person, I want my assistant to stay connected while I keep using it, for up to 12 hours from
sign-in, so that I don't reconnect every 10 minutes, while a connection left unused lapses after 30 minutes, just as
an app session does.

### Acceptance criteria
Already specified elsewhere (linked, not copied):
- [mcp-server.md §4.1](../../mcp-server.md#41-settings) row *Refresh token*; §4.6 rows *30 minutes without using the
  connection…* and *The person disconnects Grow2Notes…*.
- §10 item 4, the refresh and revocation cases: reuse outside and inside the leeway, after 30 minutes, after 12
  hours, and for a user since deactivated, reset or made a worker.

Specific to this story:
- [ ] Refresh tokens rotate and are single use, with reuse detection and the leeway chosen in S07.01.03. They are
      issued as S07.01.03 decided when a client does not ask for `offline_access`.
- [ ] Given a refresh more than 30 minutes after the last one, then it is refused. Given a refresh more than 12 hours
      after `auth_time`, then it is refused, however recently the token was used.
- [ ] The refresh handler rebuilds the principal from the user row. Given a user since deactivated, reset or made a
      worker, then the refresh fails and their authorisations are revoked.
- [ ] The revocation endpoint accepts a refresh token from a public client with no secret.

### Notes
- Whether each assistant refreshes only when used, and whether it calls the revocation endpoint, is recorded by the
  manual tests (S07.05.03).
