# F01.03 Common items and groups

**Outcome:** managers keep the organisation's common items in groups on one screen: the built-in Every note group is
always first and cannot be renamed, moved or archived; other groups are added, renamed, reordered, archived and
restored; items are added, reworded, reordered, moved to another group, archived and restored (D44, D45, A41–A43).
Nothing is deleted.

## Stories
- S01.03.01 Every note group, built in
- S01.03.02 Add and reword common items
- S01.03.03 Reorder common items in a group
- S01.03.04 Archive and restore common items
- S01.03.05 Add and rename groups
- S01.03.06 Reorder groups
- S01.03.07 Archive and restore groups
- S01.03.08 Move a common item to another group

## Feature checks
Owns these rows in [coverage.md](../coverage.md):
- design.md §14 M1 *Scope*, "the organisation-wide common items in their groups (groups: add, rename, reorder,
  archive, restore; items: add, reword, reorder, move to another group, archive, restore; the built-in Every note group
  created with the organisation, D44, D45)".
- design.md §14 M1 *Done when*, "The Every note group cannot be renamed, moved or archived, and a second one cannot be
  created (API and database tests)." The database tests are in S01.03.01; the API tests in S01.03.05, S01.03.06 and
  S01.03.07.
- `common-items.md › Content and copy`, `› Layout`, `› Loading, empty, errors`, `› Reordering`, `› Add, edit, rename,
  move`, `› Archive and restore`, `› Failures and conflicts`.

### Acceptance criteria
Already specified elsewhere (linked, not copied):
- design.md §4.9 item 4 (the item list, "New item in [group name]", Add item).
- [common-items.md](../../ux/screens/common-items.md) › Acceptance criteria › Add, edit, rename, move, these bullets:

  wording part) and "Line breaks typed or pasted…".
- common-items.md › Acceptance criteria › Failures and conflicts, these bullets for items: "With the network cut…",
  "A `412` on an item Save…" and "A `401` during any write…".

Specific to this story:
- [ ] `POST /api/admin/common-item-groups/{groupId}/items` adds the item at the end of an active group and writes
      `common_item.created`; for an archived group it returns `409 config.group_archived`.
- [ ] `PUT /api/admin/common-items/{id}` with an unchanged group needs `If-Match` and writes `common_item.updated`
      with the old and new wording; it returns `409 config.group_archived` when the item's group is archived.
- [ ] The server also saves line breaks as single spaces.

### Notes
- Owner answer, 13 October 2026: A45, which this story cites, and the 200-character limit (A6) are confirmed as written
  (D82).
- From S01.01.01 (13 October 2026, its whole-branch review): the endpoints go in the `/api/admin` group with their
  matrix rows, and the handler class, in `Features/CommonItems`, takes an `Actor`. The `POST` puts the item at
  `ListOrder.End` of its group's items, one more than the highest active `SortOrder` (A2), and saves it with
  `common_item.created` through `ConfigurationChanges.SaveAsync`, given no values before, so `Details` hold `new`
  alone. The `PUT` loads the item through the tenant filter, so another organisation's is `404`; checks `If-Match`
  with `IfMatch.Check`, given `request.Headers.IfMatch` and `RowVersionToken.Of(item)`, the endpoint answering the
  code it gives with `code.Problem()`; and saves `common_item.updated` the same way, given `text` before and after.
  Its `PreconditionFailed` is `412`, and a `PUT` of the stored text saves nothing and writes no event (D84).

As a manager, I want to move a common item up or down within its group, so that items show on notes in a sensible
order.

### Acceptance criteria
Already specified elsewhere (linked, not copied):
- [common-items.md](../../ux/screens/common-items.md) › Acceptance criteria › Reordering, the bullets for item rows:
  "Move up on row 2 of a group…", "Move down on row 1…", "End buttons…", "Two quick presses…" and "The screen never
  shows a new order…".
- common-items.md › Acceptance criteria › Layout, the bullets for item rows.
- common-items.md › Acceptance criteria › Failures and conflicts, the bullet "A `412` on any group write… or a `422
  config.order_mismatch`…" (the order part).

Specific to this story:
- [ ] `PUT /api/admin/common-item-groups/{groupId}/items/order` with the group's active item IDs rewrites their order
      and writes `common_item.reordered`; any other set returns `422 config.order_mismatch`.

### Notes
- From S01.01.01 (13 October 2026, its whole-branch review): the endpoint goes in the `/api/admin` group with its
  matrix row, and its handler class, in `Features/CommonItems`, takes an `Actor`. It reads the group's active items
  with the groups list's SQL, `ORDER BY SortOrder, CreatedAtUtc, Id`, and gives them and the requested IDs to
  `ListOrder.Reorder`, which never sorts them itself (F01.01, S01.01.01's Notes, *Reorder*); its `OrderMismatch` is
  `422 config.order_mismatch`. Otherwise it saves `common_item.reordered`, with no `EntityId`, through
  `ConfigurationChanges.SaveAsync`, given the result's `Before` and `After` and the `groupId` as an extra key, which
  `Details` hold beside the old and new `order`; the order already stored saves nothing and answers `204` (D84). The
  save's `PreconditionFailed`, an item that another request changed after this one read the list, is answered as
  `422 config.order_mismatch` too, not the `412` its `Error` names, as a reorder sends no `If-Match` and the screen
  re-reads the list for both (list-editor.md *Request errors*). A test on SQL Server shows it with two scopes, as
  S01.01.01's race test in `ConfigurationChangesOnSqlServerTests` does, and no order or event is written.
- From S01.01.01 (13 October 2026, its second whole-branch review): S01.01.01 ticked its criterion for a missing,
  extra, archived or repeated ID at `ListOrder.Reorder`, on stand-in rows, and left each reorder endpoint to show it
  on its table, as this story's criterion's "any other set" does for the items. A test on SQL Server sends each of
  the four, the extra one an item of another group, and finds `422 config.order_mismatch`, every item's `SortOrder` as
  it was and no `common_item.reordered`. `ListOrder.Reorder` refuses an archived ID only as one it was not given, so
  the handler gives it the group's active items alone.
