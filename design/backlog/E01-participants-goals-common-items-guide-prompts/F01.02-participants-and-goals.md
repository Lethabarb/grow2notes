# F01.02 Participants and goals

**Outcome:** managers keep the participant list (add, correct, archive and restore participants) and each
participant's flat list of goals (add, reword, reorder, archive and restore goals), on a phone or a laptop (D8, A5).

## Stories
- S01.02.01 See and find participants
- S01.02.02 Add a participant
- S01.02.03 Correct a participant's details
- S01.02.04 Archive and restore a participant
- S01.02.05 Add goals for a participant
- S01.02.06 Reword a goal
- S01.02.07 Reorder goals
- S01.02.08 Archive and restore goals

## Feature checks
Owns these rows in [coverage.md](../coverage.md):
- design.md §14 M1 *Scope*, "manager screens for participants (add, edit, archive, restore)" and "each participant's
  goals".
- design.md §14 M1 *Done when*, "A manager can set up a participant with five goals on a phone without help."
- `participants.md › Access and privacy`, `participants.md › Participants list`, `participants.md › Add participant
  and Details`, `participants.md › Goals`, `participants.md › Archive and Restore`.

Feature-level check: the "five goals on a phone without help" line is a manual check in test, by a manager who has
not used the screen before, on their own phone.

Other participants.md groups: Write past-day note is E02's (design.md §14 M2, past-day notes); Cross-cutting is a
Definition of Done row. The participant detail's Past notes and Write past-day note actions arrive with E02
(S02.04.02, S02.08.01), and its Export record action with S05.01.01.

### Notes
- The bullets "gone from Today" and "back on Today", and the archived view's Past notes and Export record actions,
  are checked when S02.01.01, S02.04.02 and S05.01.01 add Today, Past notes and Export record.

  S07.03.02, as the Note above assumed (D86). This story's criteria stand.
- From S01.01.01 (13 October 2026, its whole-branch review): the endpoints go in the `/api/admin` group with their
  matrix rows. The handler takes an `Actor`, loads the participant through the tenant filter and checks `If-Match`
  with `IfMatch.Check`, as S01.02.03's Note from S01.01.01 says. Archive calls `Archiving.Archive`, which sets
  `ArchivedAtUtc` from `TimeProvider`, and sets `Status` beside it; restore sets `Status` back and clears
  `ArchivedAtUtc` itself, as `Archiving.Restore` is for a row of an ordered list. Each saves through
  `ConfigurationChanges.SaveAsync`, given `status` and `archivedAtUtc` before and after, and archiving an archived
  participant or restoring an active one saves nothing, writes no event and answers `204` (D84).

As a manager, I want to move a goal up or down, so that goals show on notes in the order that suits the participant.

### Acceptance criteria
Already specified elsewhere (linked, not copied):
- [participants.md](../../ux/screens/participants.md) › Acceptance criteria › Goals, these bullets: "After Move down on
  row 1…", "Move up on row 1 and Move down on the last row…", "Goal rows use the wrapping flex layout…" and "Two quick
  presses on different rows…".

Specific to this story:
- [ ] `PUT /api/admin/participants/{participantId}/goals/order` with the full active ID set rewrites the order and
      writes `goal.reordered` with the old and new order.
- [ ] Given a list with a missing goal ID, an extra one (another participant's), an archived one or one repeated, then
      `422 config.order_mismatch` and nothing changes: no `SortOrder` or `goal.reordered` is written.
- [ ] The screen never shows a new order before the server confirms it.

### Notes
- From S01.01.01 (13 October 2026, its whole-branch review): the endpoint goes in the `/api/admin` group with its
  matrix row, and its handler class, in `Features/Participants`, takes an `Actor`. It reads the participant's active
  goals with the goals list's SQL, `ORDER BY SortOrder, CreatedAtUtc, Id`, and gives them and the requested IDs to
  `ListOrder.Reorder`, which never sorts them itself (F01.01, S01.01.01's Notes, *Reorder*); its `OrderMismatch` is
  `422 config.order_mismatch`. Otherwise it saves `goal.reordered`, with the `ParticipantId` and no `EntityId`,
  through `ConfigurationChanges.SaveAsync`, given the result's `Before` and `After`; the order already stored saves
  nothing and answers `204` (D84). The save's `PreconditionFailed`, a goal that another request changed after this
  one read the list, is answered as `422 config.order_mismatch` too, not the `412` its `Error` names, as a reorder
  sends no `If-Match` and the screens re-read the list for both (list-editor.md *Request errors*). A test on SQL
  Server shows it with two scopes, as S01.01.01's race test in `ConfigurationChangesOnSqlServerTests` does: a goal
  that one scope changes after the other read the list gives the other's reorder that `422`, and no order or event is
  written.
- From S01.01.01 (13 October 2026, its second whole-branch review): S01.01.01 ticked its criterion for a missing,
  extra, archived or repeated ID at `ListOrder.Reorder`, on stand-in rows, and left each reorder endpoint to show it
  on its table, so this story has the criterion for the goals (the second). A test on SQL Server sends each of the
  four, the extra one another participant's goal, and finds `422 config.order_mismatch`, every goal's `SortOrder` as
  it was and no `goal.reordered`. `ListOrder.Reorder` refuses an archived ID only as one it was not given, so the
  handler gives it the active goals alone, never the list that `includeArchived` reads.
