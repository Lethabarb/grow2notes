# F01.01 Configuration rules

**Outcome:** every setup endpoint for participants, goals, common items, common item groups and guide prompts is
manager-only, versioned with an ETag, has no delete, and writes its audit entry with old and new values, through one
shared mechanism that Release 2 can reuse (mcp-server.md §3.5).

## Stories
- S01.01.01 Shared configuration handling

## Feature checks
Owns these rows in [coverage.md](../coverage.md):
- design.md §14 M1 *Scope*, "Workers cannot reach any of these." and "Every change is audited."
- design.md §14 M1 *Done when*: "A worker calling any configuration endpoint gets `403` (automated test)"; "There is
  no delete endpoint for any of these"; "Every change writes an audit entry with old and new values."

Feature-level check: before E01 closes, the configuration stories' tests together cover every configuration event
in design.md §5.4, each found with its old and new values.

Enabler: the configuration endpoints' shared parts: the `/api/admin` group behind the `Manager` policy; handler
classes that take the acting user and the channel; `RowVersion` exposed as a base64 `rowVersion` and ETag and checked
against `If-Match` (with the helper from S00.03.04); an audit helper that records old and new values in `Details`; a
reorder helper (active rows rewritten as 0 to n-1, `422 config.order_mismatch` when the ID set is not the active set);
and archive and restore helpers (a restored row goes to the end). So that participants, goals, common items, groups and
guide prompts follow the same rules with little code each, and Release 2's tools can call the same handlers.

  - **Handlers answer with a §6.9 code, not an HTTP result,** so that an MCP tool can give the same code
    (mcp-server.md §5.5 uses `precondition.required`, `precondition.failed` and `config.order_mismatch` too), and the
    endpoint answers the code's `Problem()`. So `IfMatch.Check` takes the `If-Match` values the request sent, not the

    unchanged; nothing in the app calls it today, and any caller that `main` has by then (S00.06.03's resend onwards)
    is changed to answer the code's `Problem()`, with its tests run again. A handler loads the row through the tenant
    filter first, so another organisation's row is `404` before any `428` or `412`, then checks the version, then
    works out what changes. Release 2's tools pass their `expectedVersion` as its ETag (`IfMatch.ETag`);
    mcp-server.md §5.1's no-op "whatever the version" is theirs to add.
  - **One save.** The change and its audit event are saved by one `SaveChanges`, the audit writer's, so they commit
    or fail together without `InTransactionAsync`, which design.md §5.9 keeps for work of several saves. A save that
    throws `DbUpdateConcurrencyException`, because the row changed after it was loaded, writes neither and gives
    `412 precondition.failed`; so does a row made up with another organisation's key (A48), never `500` (the S00.03.04
    Note above, with `IfMatch.Check` now giving the code).
  - **Nothing to change, nothing written.** D84's rule for the guide prompts holds for every configuration row, as
    mcp-server.md §5.1's `changed: false` does for every tool: after any version check, a `PUT` of the stored values,
    archiving an archived row, restoring an active one and a reorder to the order already stored save nothing, write
    no event and answer as a save does (`200` with the same `ETag`, or `204`).
  - **Old and new values.** `Details` holds `{"old": {…}, "new": {…}}` with only the values that changed, named and
    written as the row's list in design.md §6.6 gives them (`text`, a group's `name`, `sortOrder`, `archivedAtUtc`, a
    participant's `givenName`, `familyName`, `dateOfBirth` and `status`, a common item's `groupId`), never `id` or
    `rowVersion`. A null value is written as JSON `null`, so archiving gives `"old": {"archivedAtUtc": null}`, and a
    new row's event has `new` alone, with all of them, nulls included, so every new row of a type has the same keys.
    Other keys go beside them, such as a reorder's `groupId` and Release 2's `via`, `client` and `tool` (mcp-server.md
    §9). Configuration rows hold no note text, so none can reach `Details` (A28).
  - **Reorder.** The requested IDs must be each active row of the list exactly once; a missing, extra (unknown,
    another list's or archived) or repeated ID is `422 config.order_mismatch`, with no row changed. Otherwise the
    active rows get `SortOrder` 0 to n-1 in that order. A row changed between loading and saving makes the save fail,
    as above, and a reorder answers that with `422 config.order_mismatch` too, not `412`, as it sends no `If-Match`
    and the screens re-read the list for both (list-editor.md *Request errors*). Each reorder endpoint makes that
    mapping and tests it on its own table (*What later stories take*), as the helper is pure and this story has no
    list table to show it on. Rows with the same `SortOrder`, which two adds at once can give, are read
    in `CreatedAtUtc`, then `Id`, order: the lists and the reorder read them with the same SQL
    `ORDER BY SortOrder, CreatedAtUtc, Id`, and the helper takes the rows in the order that query returns them and
    never sorts them itself, as SQL Server orders `uniqueidentifier` values differently from .NET's `Guid`. A
    `*.reordered` event's `EntityType` is the rows' type and its `EntityId` empty, as it is about a list: a
    participant's goals are named by `ParticipantId`, a group's items by `groupId` in `Details`, and the groups need
    neither; its `Details` hold the old and new `order`, the active IDs.
  - **The end of a list** is one more than the highest active `SortOrder`, or 0 for a list with none, since archiving
    leaves gaps that only a reorder closes, and a row put at the count could tie with one already there. Adding,
    moving an item to another group and restoring use it (A2, A42). Archive sets `ArchivedAtUtc` from `TimeProvider`
    and leaves `SortOrder`; restore clears it and puts the row at the end. A participant, in no ordered list, archives
    on the same `ArchivedAtUtc`, with its `Status` set beside it by S01.02.04.
  - **Proving it before any configuration table exists.** `Organisation` is the one configuration row in the model
    with a `RowVersion` (the guide prompts' ETag, design.md §6.7), so the save's tests change its guide prompts through
    test-only endpoints in the admin group, as S01.04.01's will, in an organisation each test adds, so that no seeded
    row changes. The list helpers are pure, so unit tests on stand-in rows show them, and each endpoint that adds,
    reorders, archives or restores shows them again on its own table (S01.02.04, S01.02.05, S01.02.07, S01.02.08 and

    of them failing.
